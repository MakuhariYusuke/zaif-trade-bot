## §0 総評

00/01 は v459 反省をかなり正しく吸収しており、**v460の起点として十分に強い**。  
ただし現時点では、以下 5 点を補正しないと再び判定が歪む可能性が高い。

1. G1 の多重比較制御が不足（偽陽性リスク）
2. 統計仕様（Holm）と 001 のコード例が不一致
3. maker-only の執行定義が曖昧（fillの質が未定義）
4. 欠損処理が市場レジームを歪める可能性
5. reproducibility の実装要件（seed/依存関係固定）が不足

---

## §1 重大指摘（優先順）

| Severity | 指摘 | 該当 | 影響 | 修正提案 |
|---|---|---|---|---|
| **CRITICAL** | G1 で「9組合せのどれか1つPASS」を許容する一方、明示的な多重比較補正がない | 000# §3.2, §3.7 | 偽陽性で Gate 通過する | G1判定に Holm-Bonferroni を明記し、`family = horizon × target × model` で補正 |
| **CRITICAL** | 統計仕様は Holm 前提だが、001 のコード例は単発 Mann-Whitney + Cliff のみ | 000# §3.7 vs 001# §5 | 実装が仕様逸脱しやすい | 001 に Holm 適用コード例を追加（複数baseline同時比較） |
| **HIGH** | maker-only 前提だが、fill率の「量」しかなく「質」（ adverse selection / post-fill drift ）がない | 000# §3.3 | fillしても負ける注文を拾う恐れ | `post_fill_30s_pnl` と `maker_fill_quality` を G1.1 に追加 |
| **HIGH** | 欠損時に行除外が多く、閑散相場を系統的に捨てる設計になっている | 001# §1.3 | 学習分布と実運用分布がズレる | 欠損フラグ列を追加し、除外ではなく「マスク + フラグ特徴量」で処理 |
| **HIGH** | `n >= 16` 規定と、G1の5分割評価の関係が未定義 | 000# §3.7, §3.2 | Gate 判定の一貫性が崩れる | G1専用の最小サンプル規定（例: 5 folds × 4 seeds = 20）を別途明文化 |
| **MEDIUM** | G2 の `gross>0 seed比率` は単純すぎる | 000# §3.4 | ばらつきの大きい偶然通過が起きる | worst-seed下限（例: ROI > -2%）と分散上限を追加 |
| **MEDIUM** | G3 で PF を「全seed平均」で見るのは統計的に弱い | 000# §3.5 | 平均値が外れ値で歪む | median + worst-seed + pooled の3指標併記に変更 |
| **MEDIUM** | `run_id` はあるが依存関係ハッシュ（requirements/lockfile）がない | 001# §4.3 | 再実行時に同条件を再現できない | manifest に `deps_hash`, `python_version`, `torch/cuda` を追加 |
| **LOW** | 00/01のファイル命名は新規則準拠だが、`001` の subject が広く、将来の追跡性が落ちる | 001 filename | 参照粒度が粗い | 将来は `001_ph0_plan_data_contract.md` への改名を検討 |

## §2 良い設計（維持推奨）

1. **Gate 順序の是正**  
   - v459 の逆順（後で情報量検証）を修正し、G1-info を早期化した点は正しい。  
2. **manifest 強制**  
   - 文書再現ではなく成果物再現へ寄せた設計は妥当。  
3. **docs / prompts / experiments 分離**  
   - v459 の文書膨張問題に対する実効策。  
4. **Phase と Gate の名称固定**  
   - 00# の参照安定性が高まる。

## §3 実装前チェックリスト（v460 Day1 推奨）

1. G1 の多重比較補正ロジックを `run_gate_check.py` に実装。
