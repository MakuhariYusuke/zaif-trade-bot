## 2. 重大な残課題（修正必須）

### 2.1 Parquet統合の実装前提が未整理
計画では「UnifiedTrainerにParquet自動検出を追加」とありますが、  
**実装経路が2系統（SAC側 / UnifiedTrainer側）**に分かれており、  
**ABRewardExperiment側の修正だけでは効果が出ない**点は依然として重要です。

**具体的な注意**:
- SACTrainerは独自の `_load_data_with_format_detection()` を持つ  
- UnifiedTrainerにも `_load_data_with_format_detection()` があるが、  
  **通常の訓練パスで呼ばれるかが不明瞭**  

**修正提案**:
1. **“訓練データ読込は必ずこの関数を通る”**という設計保証を明記  
2. SACTrainer/UnifiedTrainerの**二重経路を一本化**する方針を追記  

### 2.2 MTF無効化は「設定だけ」でなくコード修正が必要
修正版ではコード修正を前提にしたのは良いが、  
**実際に強制有効化を解除するコミットがPhase 4の前提条件**です。  
“計画に書いた”だけでは効かないため、**前提条件として明文化**してください。

### 2.3 Parquet使用時の「特徴検出ロジック」が曖昧
`feature_cols >= 5` で“事前計算”と判定するのはリスクが高いです。  
**誤検出（不完全特徴データ）**で学習が崩れる可能性があります。

**改善案**:
- 事前計算フラグを明示（例: `precomputed_features: true`）  
- 必須列（OHLCV + timestamp + required_features）チェックを厳密化

## 3. 中程度の懸念（調整推奨）

### 3.1 “8特徴削減”は基盤計画に組み込むには早い
計画上は **A/B検証をWeek 1に実施**するため妥当だが、  
**8特徴という具体値が“成果前提”に見える**書き方になっています。  
**「8特徴は仮説」**であることを明確にすると安全です。

### 3.2 再現性指標の許容幅
**ROI±5% / Sharpe±0.2**は妥当だが、  
**過去実験のばらつき実測値**に基づく根拠があると説得力が増します。

### 3.3 統計検定のサンプル数前提
「n≥16（4seed×4split）」は妥当だが、  
**Phase 3.5で8特徴に削減した場合の収益分散**が増える可能性があり、  
**nを固定とするなら“検出力の評価”**を追記すると良いです。
