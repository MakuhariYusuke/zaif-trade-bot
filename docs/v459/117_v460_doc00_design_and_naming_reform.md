## §2 v459 命名法則の致命的問題

### §2.1 ファイルソート崩壊

2 桁連番 `NN_` が 100 を超えた時点で、ファイルシステムの辞書順ソートが破綻:

```
00_ 01_ ... 09_
100_ 101_ ... 116_    ← 3桁がここに割り込む
10_ 11_ ... 19_
20_ ... 99_
```

`10_phase1_specification_review.md` が `116_phase_e0_diagnostic_report.md` の**後**に表示される。v455–v458 は 2 桁で収まったため顕在化しなかった。

### §2.2 Phase 帰属の消失

117 文書中、ファイル名に Phase 帰属がない「遊離文書」:

| 番号範囲 | 例 | 本来の帰属 |
|---------|---|-----------|
| 34# | `windows_sigint_resolution...` | Phase 3 |
| 35–38# | `feature_generation_optimization...` | Phase 3 / 3.5 |
| 47–49# | `current_position_summary`, `external_advice_*` | Phase 4 |
| 53# | `time_optimization_strategies` | Phase 4 |
| 54–61# | `ai_review_prompt*` | Phase 4 (外部レビュープロンプト) |
| 65–66# | `review_validity_assessment`, `doc00_consistency_check` | Phase 4 |

これらはファイル名だけでは Phase を特定できず、索引がなければ文脈喪失する。

### §2.3 ファイル名衝突

| 衝突 | 実態 |
|------|------|
| `41_phase4_planning_review.md` = `42_phase4_planning_review.md` | 42 は再レビューだが名前同一 |
| `57_` = `58_` = `59_` (`ai_re_review_prompt_review.md`) | 3 文書同名 |
| `70_` = `71_` (`day8_scale_deconfounding_review.md`) | 2 文書同名 |

### §2.4 レビューチェーン命名の不統一

レビュー対応文書の命名が 3 パターン混在:

```
初期:  15_doc14_review_response.md     (doc + 番号 prefix)
中期:  99_98_review_validation_...md    (裸番号 prefix)  
後期:  114_113_review_phase_...md       (裸番号 prefix)
```

`doc` prefix の有無、対象番号の表記位置が一貫しない。

### §2.5 Phase 命名体系の断絶

```
Phase 0 → 1 → 2 → 3 → 3.5(!) → 4 → 4.5(!) → B → C → D → E
```

数字体系が飽和し、アルファベットに逃げた結果、00# の Phase 0–6 定義と完全に乖離した。

### §2.6 日英混在

`39_review_response_修正計画.md` のみ日本語。1 件だが規則性を破壊。

## §3 v460 命名規則の提案

### §3.1 ファイル名形式

```
NNN_PhX_type_description.md
 │    │    │      │
 │    │    │      └─ 英語スネークケースの内容記述
 │    │    └─ 文書種別 (後述)
 │    └─ Phase 略号
 └─ 3桁ゼロ埋め連番
```

### §3.2 Phase 略号

| 略号 | 意味 | 備考 |
|------|------|------|
| `ph0` | Phase 0: 設計・準備 | 00# 自体は `000_ph0_plan_project_proposal.md` |
| `ph1` | Phase 1 | 以降は v460 内で定義 |
| `phX` | Phase X (任意) | **数字のみ。アルファベット Phase 禁止** |
| `phG` | Phase-independent (Global) | 横断的文書: 外部レビュー等 |

**規則:**
- Phase 番号は連番 0, 1, 2... のみ。小数 (3.5) 禁止
- Phase 計画変更時は「Phase 再定義文書」を発行し、旧定義を廃止

### §3.3 文書種別 (type)

| type | 略記 | 用途 | 例 |
|------|------|------|-----|
| `plan` | 計画 | 仕様書、設計書、実行計画 | `005_ph1_plan_feature_pipeline.md` |
| `rev` | レビュー | 外部/自己レビュー | `006_ph1_rev_005.md` |
| `resp` | 対応 | レビューへの対応 | `007_ph1_resp_006.md` |
| `rpt` | 報告 | 完了報告、実験結果 | `010_ph2_rpt_xgb_baseline.md` |
| `fix` | 修正 | バグ修正報告 | `012_ph2_fix_scaler_leak.md` |
| `ext` | 外部 | 外部レビュー・助言 | `015_phG_ext_review.md` |
| `meta` | メタ | 現状整理、索引、Phase 再定義 | `020_phG_meta_phase_redefine.md` |

**規則:**
- `rev` と `resp` は対象文書番号を含める: `rev_NNN`, `resp_NNN`
- これにより `doc` / 裸番号混在を解消
- `ext` は外部から受領した文書を明示的に区別

### §3.4 AI プロンプト文書の扱い

v459 では 54–61# の AI レビュープロンプト群 (8 文書) が本体ディレクトリを膨張させた。

**v460 方針:** `prompts/v460/` に分離。`docs/v460/` には含めない。

### §3.5 日次実験ログの扱い

v459 Phase 4 の `dayX_` 命名（62#, 67#, 69# 等）は 20 文書以上を生成した。

**v460 方針:**
- 日次実験は `experiments/v460/` に分離
- `docs/v460/` には Phase 境界の「完了報告」(rpt) のみ残す
- 目標: `docs/v460/` は **40 文書以内**

## §5 v460 特有の考慮事項

### §5.1 Gate 1 を最初に定義する理由

v459 の最大教訓は「特徴量を先に検証せよ」(K2)。v460 の Gate 体系は:

```
Gate 1: 特徴量情報量  ← 最初に実行。FAIL なら即 No-Go
Gate 2: 技術品質       ← Gate 1 通過後のみ
Gate 3: 収益性         ← Gate 2 通過後のみ
Gate 4: 実行品質       ← Gate 3 通過後のみ
```

v459 は Gate 2 (技術検証) から始めてしまい、Gate 1 (K2) を最後に実行した。この順序の逆転が数百時間の浪費の根本原因。

### §5.2 00# に含めるべき v459 参照

v460/00# §1 から以下を**リンクのみで**参照:

| 参照先 | 内容 | 用途 |
|--------|------|------|
| `../v459/index.md` | v459 全文書索引 | コンテキスト復元 |
| `../v459/116_phase_e0_diagnostic_report.md` §17 | v459 最終総括 | 根本原因の原典 |
| `../v459/116_phase_e0_diagnostic_report.md` §16 | K2 結果 | Gate 1 設計の根拠 |

### §5.3 maker-only 前提の明記

v459 Oracle テスト (E1) で taker 0.1% は完全予測でも不成立が確定した。v460/00# §0 に以下を明記:

> **前提条件**: 全取引は Zaif maker 注文 (手数料 0%) で執行する。taker 注文は禁止。

これは §3 Gate 定義にも反映し、taker 混入は Gate FAIL とする。

## §6 批判的検討

### §6.1 命名規則は本当に問題の根本か

命名規則の改善は**索引性・可読性の向上**に寄与するが、v459 の失敗原因は命名ではなく**特徴量情報量の不足**だった。命名改革に過度なコストを投じるのは本末転倒。

**結論**: 命名規則は §3 の水準で十分。自動索引生成スクリプトや YAML frontmatter は過剰投資。ファイル名に Phase と type を含め、3 桁連番にする — これだけで v459 の問題の 90% は解消する。

### §6.2 00# の簡潔化は両刃の剣

v459 00# が 419 行もあったのは冗長だが、§5 の Gate 定義が詳細だったからこそ Phase E まで一貫した判定基準を維持できた。

**結論**: Gate 定義 (§3) は詳細を維持する。それ以外を削る。結果として 150 行でも Gate §3 が 60–80 行を占めてよい。

### §6.3 Phase 固定は適応力を殺すか

v459 では Phase 計画が崩壊し、Phase B–E にピボットしたことで結果として K2 の有効な実験に到達できた。Phase 固定はこの柔軟性を殺すリスクがある。

**結論**: Phase 番号は固定するが、Phase の中身（目標・スコープ）は改訂可能にする。「Phase 3 の目標を変更」は許可するが、「Phase 3.5 を挿入」は禁止。変更時は 00# §2 の改訂 + Appendix A に記録で追跡性を担保。

### §6.4 文書数 40 以内は現実的か

v459 は 117 文書に膨張した。しかし Phase 4 だけで 47 文書 (40–86#) を生成している。これは日次実験報告・AI プロンプト群の docs/ 混入が原因。

**見積**:
- Phase 0: plan + rev + resp + rpt ≈ 4 文書
- Phase 1–N: 各 4–6 文書 × 5 Phase = 20–30 文書
- phG (横断): ext + meta ≈ 5 文書
- 合計: 29–39 文書 → **40 以内は実現可能**（日次ログ・プロンプトを分離する前提）

## §8 結論

| 項目 | v459 | v460 方針 |
|------|------|----------|
| ファイル名連番 | 2 桁 (`NN_`) | **3 桁 (`NNN_`)** |
| Phase 帰属 | ファイル名に不在の場合あり | **全ファイルに `PhX_` 必須** |
| 文書種別 | 暗黙的 | **`type_` を明示** |
| レビューチェーン | `docNN` / 裸番号混在 | **`rev_NNN` / `resp_NNN` 統一** |
| Phase 体系 | 数字→小数→アルファベット混在 | **数字のみ、挿入禁止** |
| 日英混在 | 1 件あり | **英語のみ** |
| 00# 分量 | 419 行 | **150 行以内** (Gate §3 は詳細維持) |
| 00# の Gate 順序 | Gate 1=技術 → Gate 2=収益 | **Gate 1=特徴量情報量 (最優先)** |
| AI プロンプト | docs/ 内 | **prompts/ に分離** |
| 日次実験ログ | docs/ 内 | **experiments/ に分離** |
| 文書数目標 | 117 (上限なし) | **40 以内** |
