# 36. 特徴生成最適化計画レビュー（Phase 3.5）

**対象**: `docs/v459/35_feature_generation_optimization_plan.md`  
**日付**: 2026-01-26  
**結論**: 方針は妥当。ただし前提計算・スクリプト実体・既存実装活用の整理が不足。  

---

## 1. 総評（先に結論）

現状のボトルネックが「特徴生成」である点と、**Phase 3.5を挿入して改善を図る判断は妥当**です。  
ただし、**時間見積りの前提が誤っている可能性**が高く、**最も効く改善は“再計算の回避（キャッシュ/再利用）”**です。  
Numbaやベクトル化は有効ですが、**「どの計算が本当に重いか」**の可視化と、**既存実装の最大活用**が先決です。

---

## 2. 良い点（継続すべき）

- **ボトルネックの明確化**（特徴生成 63.7%）
- **Tier構成**で“やり過ぎない”段階的最適化
- **検証観点（性能・精度・再現性）**が揃っている
- **Phase 3計画への影響評価**がある

---

## 3. 重大な懸念（修正推奨）

### 3.1 時間見積りの前提が不整合
5,000ステップの総時間をそのまま50,000ステップに線形拡大していますが、  
**特徴生成は「ステップ数ではなくデータ長に依存する」固定コスト**の可能性が高いです。  
つまり、50,000ステップでは**トレーニング時間が伸びる一方、特徴生成比率は下がる**はずです。  
現状の推定（22.6時間）は過大評価の疑いが強いので、**固定コスト + 変動コストの分離**を明記してください。

**修正提案（数式）**:
```
総時間 = 特徴生成(固定) + training_rate * timesteps
```
5,000ステップの内訳を分解し、50,000ステップはこれで推定するのが妥当です。

### 3.2 プロファイリングスクリプトの実体が存在しない
記載例の `run_single_experiment()` は現行コードに存在しません。  
現状の実体は `ABRewardExperiment(config).execute()` です。  
**ドキュメント内のサンプルは実際の入口に合わせて修正が必要**です。

### 3.3 sklearn依存の「特徴量削減」は現環境で失敗する可能性
現在は `ZTB_SKIP_SKLEARN=1` を恒常利用しています。  
`RandomForestRegressor` を使う分析は **SIGINT再発やImport失敗の可能性**が高いです。  
**「別環境で実行」または「相関/分散/欠損率だけで先に削減」**へ計画を修正してください。

### 3.4 Numbaの実装案がO(n²)の恐れ
`compute_ichimoku_numba()` で `np.max()` / `np.min()` を毎ステップスライスしており、  
**ループ内でO(n)処理 → 全体O(n²)** になり得ます。  
**Numbaよりアルゴリズム改善（rolling max/min をdequeで更新等）**が優先です。

---

## 4. 重要な改善提案（優先順）

### ✅ 最優先: **再計算の排除**
**同一データ・同一特徴セットで12実験を回す**ため、  
**特徴生成は「1回だけ」→ 全実験で再利用**が最も効きます。

推奨アプローチ:
- **特徴付きデータをParquet/Feather化**して保存し、以降はそれを読み込む  
- `FeatureCache`（`ztb/utils/cache/feature_cache.py`）の**利用有効化とキー設計の明確化**
- 実験ごとに同一キャッシュが当たるか検証（ログで hit/miss を出す）

期待効果: **実験12回で「431秒×12」→「431秒×1」に近づけられる**

### ✅ 既存実装の最大活用（差分を減らす）
既に以下が実装済みのため、**新規実装よりまず設定/利用の最適化**を推奨します。

- `FeatureRegistry` の **相関削減機構**
- `FeatureSetConfig` による **feature_set 切替**
- `_select_features_by_correlation_in_env`（環境内の削減）
- `FeatureCache`（ディスクキャッシュ）

**提案**: “新規削減ロジック”より、  
**`feature_set = "fast"` / `include_multi_timeframe_features=False`** のような構成を  
Phase 3.5 の「Quick Win」として使う。

### ✅ MTF特徴の最適化は「計算方式」より「事前計算」
`MultiTimeframeFeatureSystem` は `merge_asof` / resample を繰り返すため高コスト。  
**集約済みの複数時間足データを事前生成して保存**し、  
実行時は読み込むだけにする方が確実で安定します。

## 5. 具体的に直すべき記述（ドキュメント修正点）

- **Step 1のサンプルコード**: 実在しない関数参照  
  → `ABRewardExperiment` か `UnifiedTrainer(config).run()` に合わせる
- **Step 4の削減分析**: sklearn前提  
  → “別環境で実行 / 相関・分散のみで先に削減” を明記
- **効果試算**: 固定/変動コストを分離した数式で再計算
- **Numbaの前提**:  
  - compile time の影響  
  - 初回のみ遅くなる  
  - `NUMBA_CACHE_DIR` / fallback 明記
- **精度検証**: `abs diff < 1e-5` は厳し過ぎる  
  → `rtol/atol` + `equal_nan=True` で検証
- **再現性検証**: RLのCV < 1% は厳しい可能性  
  → “許容範囲の根拠 or 目標値の緩和” を追記

## 6. 次に進むための提案（実装順）

1. **プロファイル実行の整備**  
   - 実行入口の修正  
   - `ZTB_SIGINT_POLICY=ignore` で安全に実行
2. **特徴生成キャッシュの強化・再利用**  
   - 1回生成 → 12実験流用
3. **MTF特徴の事前生成**  
   - resample結果を固定ファイル化
4. **最小feature_setの導入**  
   - Phase 3.1の実験で「高速版」と「フル版」を比較
5. **Numba/ベクトル化は最後**  
   - データ量と効果が見えてから局所適用

---

## 7. 追加の注意点（将来の事故予防）

- **全特徴量を事前計算する場合、未来情報リークの有無を再確認**  
  （rolling/aggregationの方式が“未来値”を使っていないか）
- **SIGINT問題は環境起因の可能性が高いため、  
  “高速化のための並列化”は慎重に導入**（Windowsは特に）

---

## 8. 結論（Go/No-Go観点）

**Go**: 「再計算排除 + MTF事前計算 + feature_set調整」  
**No-Go**: 「Numba/C拡張の追加のみ」先行は非効率

最短で効果が出るのは **“一度計算して再利用する設計”** です。  
ここを優先しつつ、必要な箇所にだけNumbaを適用するのが最適です。
