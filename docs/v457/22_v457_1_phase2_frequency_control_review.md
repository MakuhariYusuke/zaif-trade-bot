# 22. Phase 2 Frequency Control Review (v457.1向け助言)

対象: `docs/v457/21_v457_1_phase2_frequency_control.md`  
参照: `docs/v457/17_v457_enhancement_roadmap.md`

## 1. 総評
Frequency Controlの実装確認と「間引いても黒字化しない」結論は妥当。ただし、**「モデルが悪い」だけで片付ける前に、実装上の再現性・評価の妥当性をもう一段確認すべき**。  
Roadmap 17の流れ（Phase 1の基盤整備→Phase 2動的制御）に照らすと、**Phase 2の検証は成立しているが、評価指標と前提の整合にまだ穴がある**。

## 2. 重要な確認不足（再現性・評価の妥当性）
1) **Net PnLの算出ロジック**  
   - `backtest_v456.py` の Net PnL は「推定」か「実数」か要確認。  
   - 取引ごとの **fee/slippage 実測** が無い場合、赤字額が過大/過小になる。

2) **Wrapper二重適用の副作用**  
   - 環境側に cooldown/min_delta がある場合、  
     wrapper でさらに間引くと **評価が二重に歪む**可能性がある。  
   - 「環境に任せた場合」「wrapperで強制した場合」の差分を記録すべき。

3) **Action strength が常に最大なのは学習バイアスの兆候**  
   - action が常に ±1 に張り付く場合、  
     閾値を変えても頻度が変わらないのは当然。  
   - これは「報酬スケール」または「探索バランス」の問題の可能性が高い。

4) **TTL/クールダウンと取引判定の整合**  
   - `info['position']` に同期したのは正しいが、  
     TTL/強制クローズが何回発生したかを記録しないと  
     「強制終了が頻度に影響している」事実が見えない。

## 3. Roadmap 17との整合チェック
Roadmapでは「Step 0: analyzer整備」「Step 1: Grid」「Step 2: Dynamic」の順。  
今回は Step 2 相当の Frequency Control まで進んだが、  
**Step 0/1で想定していた評価指標の整備が不足**している。  
先に Profit Factor / Expectancy / Avg Win/Loss を**固定化指標**として出せるようにすべき。

## 4. 次の方策（優先順）

### A. “モデルのせい”と結論づける前にやるべきこと
1) `trades.json` に **fee/slippage 実測**を保存  
2) **Profit Factor / Expectancy** を算出して、  
   「期待値がマイナス」なのか「コスト見積もりが過大」なのかを切り分ける

### B. Action張り付き対策（探索制御）
- `ent_coef` を固定値で下げるのではなく、  
  **行動分布が極端化する場合のみ緩和**する仕組みを検討。  
- 例: 平均|action| > 0.9 の場合は entropy を一時的に引き上げる。

### C. 強制間引きより「環境内の行動抑制」へ
- Wrapperで間引くより、  
  **環境側の cooldown / min_delta / edge判定を強化した方が学習に反映される**。  
- Phase 3での再学習時は wrapperを外す設計にした方が良い。

## 5. 結論
Frequency Controlの有効性検証は成功しているが、  
「モデルが完全に駄目」という断定にはまだ一歩早い。  
**評価指標とコスト計算の正確化を先に行い、  
期待値の負けが本当に構造的かを確定させるべき**。

次フェーズは「再学習」そのものよりも、  
**評価の厳密化 + 行動分布の歪み修正**を優先するのが安全。
