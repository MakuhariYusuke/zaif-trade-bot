## §3 005の論理点検

### §3.1 妥当な点

- **非定常性の指摘**: 妥当。fold4 が支配しており、全期間平均だけで進行判断するのは危険。  
- **volatility の疑似的優位**: 概ね妥当。方向 alpha の証拠としては弱い。  
- **G1.1 実行を並行検討**: 妥当。約定品質（fill/adverse selection）は独立価値がある。

### §3.2 補強が必要な点

- **判定の一貫性**  
  `run_experiment.py` は `g1_judgment` のみで判定し、`run_gate_check.py` は追加閾値を全ターゲット AND している。  
  同じデータでも実行経路で判定ルールが揺れる。
- **Gate 条件の過剰厳格化**  
  `run_gate_check.py` は `extra_all_pass = all(...)` としており、000# §3.2 の「1 組合せでも PASS で通過」と矛盾。

## §5 次ステップ提案（Phase1.1）

### Step 1: Gate 判定の単一化（最優先）

- 判定入口を 1 本化（`run_experiment` と `run_gate_check` のロジック統合）。
- G1 通過条件は 000# §3.2 / 001# §5.3 に合わせて  
  `∃ target: holm_pass ∧ pmean_pass ∧ |d|>threshold` を基準化。
- `min_ic/min_accuracy/min_significant_folds` は「all targets」ではなく「候補 target 単位」に適用。

### Step 2: ターゲット再編（方向性判定を明確化）

- G1 判定を二系統に分ける。  
  - `G1-direction`: direction/magnitude のみ（進行判定に使用）  
  - `G1-volatility`: volatility は補助評価（リスク/執行調整用途）
- これにより「高精度 volatility で見かけ上 PASS」を防ぐ。

### Step 3: fold4依存の再検証（頑健性チェック）

- fold4 除外再計算、rolling-origin 分割、レジーム別（低/高ボラ）再評価を追加。
- 進行基準: どの分割でも direction 系の IC が安定して正であること。

### Step 4: 実データ収集の運用可能化

- `MarketDataCollector` の `auto_aggregate` 呼び出し不整合を修正。
- 収集開始時 KPI:  
  - 欠損率 < 1%  
  - 重複 trade 率の監視  
  - 1日ごとの raw→1min 集約完了率 100%

### Step 5: 成果物スリム化

- `fold_results` は Gate 判定に必要な統計量のみ保存。  
- 生配列は debug モード限定にし、通常実験は軽量 JSON に統一。

## §6 進行判定（提案）

現時点の推奨判定は以下。

- **G2 (RL) 進行**: まだ不可  
- **G1.1 (執行実測) + 実板データ収集**: 実施可  
- **条件**: Step1 と Step4 を先に完了すること

理由: 方向 alpha の証拠が fold4 依存で弱く、かつ Gate 実装の不一致が残っているため。
