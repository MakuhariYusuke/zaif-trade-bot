## 1. Codex (301#) が見落とした「3つのHFT的盲点」

### 盲点1: 
one レジーム出血の真因は「静寂への過剰適合（Over-engineering in Silence）」
Codex (F1) は「
one を排除すると評価が楽観的になる。
oneでの執行を止めることも考えよ」と述べました。
しかし、なぜ 
one レジーム（通常、VPINが低すぎるかデータが不十分なウォームアップ時）で大出血するのかという「メカニズム」への言及が欠けています。

one とは、オーダーブックに明確な方向性や情報優位（Alpha）が存在しない「情報的真空状態」です。この状態で、微小なノイズに反応して ev_score や offset_mult を変動させて指値を動かすことは、**何もない空間で自らQueue（順番）の最後尾に並び直し続け、突発的なToxic Flowに対して自らを「最適な養分」として差し出している状態**です。
情報がない時（
one）は、予測モデル（EV系パイプライン）を**完全にバイパスし、広いスプレッドを維持して動かない『Avellaneda-Stoikov (2008) のピュア・パッシブMM』** にフォールバックするアーキテクチャが必須です。

### 盲点2: forced_buy_delay (294#) が放置した「遅延後の死（Death after Delay）」
HFT市場理論において最も恐れるべきは、これです。
Codex (F4) は 294# を「デッドロックの解消であり勝ち筋ではない」と評価しました。その通りですが、**実態はもっと残酷です**。
現在、在庫（Inventory）が限界に達し balance_forced が発動した際、相場が暴落（Toxicity高）していれば N 回遅延させます。しかし、N回待った後に結局**「指値（Maker注文）」を置くアプローチに固執しているのが致命的**です。
大抵の暴落時には、N回待った後でも落ちるナイフは落ち続けています。そこに指値を置けば、再び最悪の価格で貫かれます。
**修復（Repair）とは緊急手術です。** もしToxicityの最中に在庫修復を断行するなら、Makerとしての優位性を諦め、**「Taker（成行・クロス注文）として自らスプレッドを払ってでも即座に修復して逃げる」** というExecutionの動的切り替え（Maker/Taker非対称性）が欠如しています。

### 盲点3: オーケストレータの「AlternationTrap」と DD Guard の致命的シナジー
300# の発見#5で「DD Guard が Side に無自覚（一方が負けると全体ロットが減る）」と記載されました。これがオーケストレーターの「Buy / Sell の交互実行ループ」と組み合わさると**最悪のデススパイラル（Winner's Curse）**を生みます。
強い 	rending_up 相場で、Botは交互に Buy と Sell を出します。
1. Buy は置いて行かれるか、少ししか約定しない。
2. Sell は逆選択（Adverse Selection）を真っ当から食らって大きく損をする。
3. Sell の大敗により DD Guard（Portfolio全体の損失管理）が発動し、全体の base_lot が半分になる。
4. **結果、Trendに乗って利益を出すべき（本来ロットを張るべき）Buy側のロットが半分に減らされ、アルファが自刃する。**
トレンド相場では、負けている側の注文（またはロット）を絞り、勝っている側のロットを維持・拡大する **『Side-Asymmetric Risk Management（片側完結型リスク管理）』** に移行しなければ、「トレンドに逆張りして大損し、トレンドに乗る時は小ロット」という破滅の商材になります。

## 2. Gemini 3.1 Pro 最終提言（P0/P1 アクションの再定義）

300# の「構造修正（T1）」および Codex 301# の優先順位を支持しつつ、以下のHFT特化型改修を最優先で要求します。

### 【P0: System Eng】A/Bテストと統計基盤の完全分離
- Codex P0 に完全同意。sell と buy は構造的に従属（Dependent）しており、交互実行される以上 i.i.d ではありません。これを比較して「有意差なし」と結論づけるレポートスクリプトの出力表現自体を修正してください。

### 【P1: Market Theory】 
one レジームにおける「Passive MM フォールバック」
- レジームが 
one の場合、offset_mult の乗算パイプラインを強制的にバイパス（無視）し、固定の保守的スプレッド（例: +2.0 bpsなど）で陣地を張って動かない（Cancel & Replace を行わない）静的モードを追加してください。

### 【P1: Market Theory】「Toxic Forced Repair」の Taker 執行化
- balance_forced が発動し、かつ microprice_trend 等が自分に不利な強トレンドを示している場合、N回待った後に Maker で指値を置くのではなく、**現在の best_ask/best_bid を叩く（Aggressive/Taker 注文）ことで即座に在庫リスクを解消するロジック**を選択肢に入れてください。修復時の指値は二次災害を生むだけです。

### 【P2: System Eng】Side-aware DD Guard (非対称ドローダウン管理)
- warmup_daily_drawdown において、Pnlを合算で評価するだけでなく、buy_pnl と sell_pnl を分離管理するロジックを新設してください。被弾しているSideだけのロットを落とすことが、Directional Alpha を守る唯一の術です。

**【総括】**
現状の「評価が悪い・儲からない」理由は、アルファモデル（予測）の精度不足よりも、**「武器の振り回し方（執行アルゴリズムの固定化）」** に起因しています。予測ではなく執行（Execution）の非対称性を取り入れることで、300# が提起した矛盾は一気に氷解します。
