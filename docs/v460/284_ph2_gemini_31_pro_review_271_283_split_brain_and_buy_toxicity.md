## 1. 271#〜282# 実装のシステム工学・コード品質評価

### 1.1 [絶賛] 282# の 永久デッドロック解体
untick_side_halt() が自己参照的に状態を上書きし続けていたトラップの除去と、Inventory Escape (IE) の双方向化ロジックは、コードの流れとして非常に自然かつ強力です。これにより、270# で私が指摘した「非常口の前のバリケード（Routing Bug）」は完全に撤去されました。直近のログでも、約定（Fill）が正常に再開していることを確認済みです。

### 1.2 [苦言] 278#〜281# 品質管理（QA）の甘さとリファクタリング・リスク
Config 化に伴う NameError (_HALT_PERSIST_INTERVAL の参照未更新) や AttributeError が本番環境（あるいはそれに準じるテスト環境）の運用において即死の原因となった点は、Python などの動的型付け言語における典型的なリファクタリングの失敗です。
Unit Test（単体テスト）が 3000 件以上通っていても、「新コンフィグを読み込んで Main Loop を実際に1周回す」ような Smoke Test（Integration Test）が一つ欠けているだけでシステムは死にます。「Dry-runモードで1分間だけ走らせるCIパイプライン」の導入が急務です。

## 2. 283# Codex レビューに対するセカンドオピニオン

Codex の 283# レビューは、実データに基づく非常に優れた分析です。私も全面的に同意し、さらに市場微視構造の観点から補強します。

### 2.1 【P0】Split-Brain (run_id 二重起動) のシステムリスク
Codex が指摘した 1772714694_d20307ad と 1772714739_b393955d の時系列重複（JST 21:45〜22:37 付近）は、ターミナルからのログ解析でも確かに並行して書き込まれていることが裏付けられました。

**【なぜこれがヤバいのか】**
Market Making においては、「自身の直前の発注状況」と「取引所側のオーダーブック」を厳密に同期（Reconciliation）させなければなりません。2つのプロセスが同時に動くと、お互いの注文を「誰か他人の注文」として誤認するか、あるいは CEX に対して同時に同量の残高を使おうとして InsufficientBalanceError を連発し、最終的に Phantom Position Guard がパニックを起こします。
これは Watchdog プロセスが kill を発行したものの SIGTERM が効かず、Zombie 化したプロセスが残ったまま新規プロセスを start した等に起因する「不完全なファイルロック（File Lock Bypass）」の典型例です。

### 2.2 【分析同意】Buy側の「毒性（Toxicity）」被弾と Forced Buy 劣化
Codex 3.2 の指摘：「Buy が短期ドリフトに対し不利な位置で約定している」「Forced Buy の品質劣化」——これはまさに **Amihud (2002) Illiquidity と Glosten-Milgrom の情報非対称性モデルの無警戒さ**に起因します。
現在、Botは「BTCを上に持っていこう（Directional Alpha）」という思想のもと、必死に Buy を行って在庫を保とうとしています。しかし、その結果として「急な売り圧（Toxic Down Flow）」が来た時に、指値を避けることなく真正面からキャッチし、短期的 PnL で大きなマイナスを食らっています。

## 3. 次の確実な勝ち筋（P0 / P1 提言）

デッドロックによる停止（Liveness 問題）は解決しました。次からは「資産を守り、伸ばす（Safety & Profitability）」の真骨頂です。以下の順序でシステムを改修してください。

### 【P0】ロック機構とシングルトン（単一実行）の絶対保証
システムが儲かるかどうか以前の話です。
1. **Lock の OS レベル強化:** Pythonの portalocker や msvcrt (Windows) / fcntl (Linux) を用いた「プロセスが死ねば自動解放される強固なファイルロック」を実装し、ロック取得失敗時は絶対に起動させない (sys.exit(1)) 構造に直す。
2. **Watchdog の確実な Kill:** 前の PID に対して「本当にプロセスツリーから消えたか」を確認するループ（psutil.pid_exists 等）を組み込み、消えるまで新プロセスは待機させる。

### 【P1】Buy サイド防御（Adverse Selection Guard）の非対称な強化
現在、Sell側への防御はやりすぎなほど強化されていますが、Codex も指摘する通り「いま損を出しているのは Buy側」です。
1. **Buy 側の AS_Ratio (逆選択比率) 連動の Offset 強制拡大:**
   短期的な売り圧力（Microprice の下落速度）が一定閾値を超えた場合、強制的に Buy 注文の Offset を +3.0bps や +5.0bps といった安全圏まで引き下げる。
2. **Forced Buy での「待つ勇気」:**
   balance_forced な Buy であっても、Toxicity（Toxic Down Flow）を検知した場合はすぐに買わない。Glosten-Milgrom 判定に基づき「いま買うと損失確定」な瞬間は、数サイクル待ってから拾う（Delay Execution）。
