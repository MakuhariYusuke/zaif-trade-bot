## §0 エグゼクティブサマリ

1. `098` は「どこで負けているか」を side × wait × AS で分解できており、診断として高品質。  
2. `Non-AS +2.040bps / AS -4.920bps` は、AS 回避が最重要という主張を十分に裏付ける。  
3. ただし `sell` 側は `threshold=0.50` で skip 群の方が良い（逆選別）ため、**sell の skip 強化は現時点で保留**が妥当。  
4. まずは low-risk 修正で「判定精度と初動遅延」を潰し、その後に sell 特化モデルへ進むのが安全。

## §1 098 への評価

### 1.1 良い点

1. サンプル数の弱点（n=13）を明示し、過信していない。  
2. `run_id` 横断と `wait bucket` の交差分析があり、実運用に近い示唆になっている。  
3. 「offset を上げれば解決」という短絡を避け、選択バイアスまで踏み込んでいる。  

### 1.2 補強が必要な点

1. `sell` 側の SkipGate は逆選別の兆候があるため、buy/sell 同時強化は危険。  
2. AS horizon を 30s→60s に単純置換すると、執行品質シグナルが鈍化する可能性がある。  
3. P0 施策は「実装順」を固定したほうが因果検証しやすい。

## §3 トレーダー視点での重要論点

1. **目的関数は AUC ではなく実現スプレッド**  
   - 取引現場では「skip した集合の平均PnLが悪いか」が最重要。  
2. **sell の毒性は buy と非対称**  
   - 同じ閾値制御を side 共通で使うと、片側だけ悪化しやすい。  
3. **過剰 skip は機会損失と在庫偏りを作る**  
   - `PnL改善` と同時に `fill率` と `sideバランス` を監視する必要がある。  
4. **短期逆行と中期回復を区別する**  
   - 30s で悪くても 120s で回復する取引は、執行失敗ではなく時間軸ミスマッチの可能性がある。

## §4 推奨実行順（99 提案）

### P0（即実装）

1. warm_start で `threshold` を履歴から即復元（step降下待ちを除去）。  
2. SkipGate は一旦 `buy優先` で運用し、sell は保守設定（閾値高め or skip無効）に寄せる。  
3. fast_fill_defense を二層化（即時 proxy + 事後 PnL 判定）する。  

### P1（次スプリント）

1. regime warm_start + `window` 短縮で `unknown` 固定を解消。  
2. `time_filter` の global+side 合成化。  
3. `param_adapter` の逆順読込で O(total) I/O を削減。  

### P2（検証基盤）

1. sell 専用特徴量の再設計（skip 方向性の再学習）。  
2. 30s/120s の二軸ラベルで評価系を分離。

## §5 検証ガードレール（最低限）

1. 主指標: `net pnl bps`, `AS率`, `skip群PnL - kept群PnL`（side別）。  
2. 副指標: `fill率`, `sell/buy 約定比`, `cancel-replace率`。  
3. 中止条件: fill率が急低下し、PnL改善が確認できない設定は即ロールバック。

## §6 最終見解

`098` は次アクションの材料として十分に実戦的です。  
実装優先は **「判定ロジック修正」→「初動遅延解消」→「sell側モデル再設計」** の順が最も安全で、トレーダー視点でも期待値が高いです。
