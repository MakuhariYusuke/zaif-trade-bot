## 2. P2/P3レベルの残存課題と根本的アプローチ (Residual Architectural Issues)

### 2.1 Multiplicative vs Additive Pipeline の設計思想の乖離 (True Additive Pipeline Framework)
**【現状の課題】**  
`OffsetPipelineMixin` などにおける現在のオフセットパイプラインは、複数のファクター（ボラティリティ、インベントリ、毒性など）が乗算（Multiplicative）的、または段階的に連鎖して適用される構造になっています。監査結果によれば、各段階での計算結果が後段の入力となるため、ファクター間の相互作用（干渉）がブラックボックス化し、特定の状況下で極端なオフセット（または予期せぬスケール）を引き起こす恐れがあると指摘されています。

**【改善方針】**
- **加算型（Additive）パイプラインへの移行:** 各ファクター（Alpha, Beta, Gamma...）の寄与をベースのオフセット（例: 基本スプレッド）に対する独立した加算要素として計算し、最後に総和を取る設計（True Additive Framework）への再構築を検討します。
- これにより、各調整項目（毒性調整、在庫調整、ボラティリティ調整）の寄与度が明確になり、特定のファクターが全体のオフセットを不当に引き上げる（または引き下げる）リスクを軽減できます。

### 2.2 Toxicity (Toxic Flow) と Liquidity (Premium) の独立バッファ分離
**【現状の課題】**  
毒性（Toxicity / Adverse Selection）の回避と、流動性プレミアム（Liquidity provision）の確保が、単一または混在したロジック・バッファで処理される傾向があります。結果として、「毒性が高い相場で逃げるべきなのに、流動性プレミアムの計算がオフセットを甘くしてしまう（あるいは逆）」という衝突が発生し得ます。

**【改善方針】**
- **リスク防御（Toxicity Discount）** と **収益獲得（Liquidity Premium）** のロジックを分離し、独立したバッファまたはスコアとして評価する構造にします。
- 毒性指標（OFIの急変、MACDのダイバージェンス等）が高い場合は、Liquidity側のスコアを強制的に抑制（あるいはハードキャップ）するような、明確な優先順位・ゲーティングメカニズムを `fill_cycle_executor.py` または上位のパイプラインに導入します。

### 2.3 Inventory Skew と Preflight Limits の相関と制御
**【現状の課題】**  
`inventory_skew`（在庫の偏り）と `preflight_insufficient`（発注前の残高不足や制限）の発生条件が複雑に絡み合っています。在庫の偏りに対するペナルティがオフセットに反映される前に、残高不足によるプレフライトチェックが働き、機会損失や不要なログノイズを生むケース（あるいはその逆で、在庫極端時に無理な注文を出そうとして撥ねられるケース）が存在します。

**【改善方針】**
- **Inventory Skew の動的ペナルティ曲線の平滑化:** 在庫が一定の閾値を超えた際のペナルティ（オフセットの拡大による約定回避）を、非線形かつ滑らかな曲線（例: シグモイド関数や指数関数ベース）に改修し、プレフライト制限に抵触する前に自然とポジションの傾きを抑制するよう設計を見直します。
- **Preflight 側のスマート化:** プレフライトの段階で、現在の `inventory_skew` スコアを参照し、無駄な API コールや内部サイクルの消費を未然に防ぐ（早期リターン）仕組みを強化します。

## 4. 結論 (Conclusion)

直近の P1 バグ修正により、メトリクスの欠落や意図しない巨大オフセットの要因（`edrc`の計算順序ミス）は塞がれ、システムの健全な執行と正確なトラッキングが可能になりました。
次のステップは、収集された正確な執行データ（Execution Quality Metrics）を根拠として、ブラックボックス化しやすい「乗算型・多段連鎖型」のパイプラインを、「加算・独立評価型」のセキュアな設計（True Additive Pipeline）へとモダナイズすることです。
