## 1. 背景と目的

### 1.1 レビュー依頼の経緯

v460 は BTC/JPY の maker-only (手数料 0%) 自動取引システム。現在 Phase 2 (G1.1-exec: maker 執行可能性検証) で 168 時間の fill_test を実行中。

fill_test が 141 時間 (84%) 経過した時点で以下が判明:

1. **原初の G1.1 基準 (E1-E5) は SkipGate 導入前に策定されたため、現状と乖離**
2. **3/5 の基準が FAIL** — しかし根本原因は「戦略の問題」ではなく「基準の時代遅れ」
3. **168 時間は統計的に過剰** — 72-96 時間で十分な統計的検出力を確保可能

この状況を受け、G1.1 を **72h Kill Gate + 168h Qualification Gate** の二段階に分割する案を策定した。本依頼は、この再設計案の妥当性を外部視点で検証するもの。

### 1.2 本レビューで検証してほしいこと

- 二段階ゲートの設計原理は健全か
- 閾値の設定は適切か (甘すぎ / 厳しすぎ)
- SkipGate スキップを除外する計算方法は統計的に妥当か
- 見落としているリスクや代替案はあるか
- 000# (プロジェクト提案書) への改訂として整合性があるか

### 2.2 アーキテクチャ (簡易)

```
run_fill_test.py (2,819行)
├── FillTestConfig (80+ params, YAML 外部化)
├── _compute_maker_price()      ← offset 計算チェーン
│   ├── base: spread × offset_ratio
│   ├── side_offset / sell_guard / regime / spread_adaptive
│   └── imbalance: disabled
├── run_single_cycle()          ← 1 回の注文サイクル
│   ├── SkipGate ML 判定 (LogReg + SelectKBest)
│   ├── 注文 → ポーリング (5s 間隔, 300s timeout)
│   ├── stale order 検出 (30s 後 5bps 乖離で reprice)
│   └── 約定後 PnL 計測 (30s + E3 sampling)
├── run_continuous()            ← メインループ
│   ├── time_filter (side 別 UTC 時間帯ブロック)
│   ├── balance check → side 自動切替
│   ├── fast_fill_defense (即約定防御)
│   └── param_adapter (方策 A: offset 自動適応, 50 cycle 毎)
└── 補助モジュール
    ├── param_adapter.py (offset 自動調整)
    ├── skip_gate.py (ML adverse selection 分類器)
    └── fill_quality.py (FillRecord, g1_1_judgment)
```

### 2.3 SkipGate について

SkipGate は **091# Codex レビュー提案** で導入された ML ベースのフィルタ。板スナップショットから adverse selection (逆選択) の確率を推定し、高リスク局面で注文を **意図的にスキップ** する。

- 全 1,057 サイクル中 86 件 (8.1%) が `skip_gate` でスキップ
- **重要**: SkipGate は 000# §3.3 (G1.1 基準) 策定後に導入されたため、原初の E1-E5 基準には考慮されていない

## 5. 問題提起: 現行 G1.1 基準の不整合

### 5.1 基準 vs 実測の乖離

| # | 指標 | 閾値 | 実測 (141h) | 判定 | 原因分析 |
|---|------|------|-----------|------|---------|
| E1 | fill rate | ≥ 90% | 67.8% | **FAIL** | SkipGate skip + timeout が fill 分母に含まれる |
| E2 | cancel ratio | ≤ 30% | 32.2% | **FAIL** | SkipGate の意図的スキップが cancel に計上 |
| E3 | queue wait | ≤ 60s | 12.8s | PASS | — |
| E4 | PnL30 mean | ≥ 0 (有意) | -0.196 bps (p=0.161) | PASS | 有意に負ではない |
| E5 | AS ratio | ≤ 20% | 31.4% | **FAIL** | 閾値が厳しすぎる可能性 |

### 5.2 根本原因: SkipGate は基準策定後に導入された

000# §3.3 (G1.1 基準) は **2026-02-13 に策定**。SkipGate は **091# Codex レビュー (2026-02-18)** で提案・導入。

原初の基準は「全注文が約定を試みる」前提で設計されたが、SkipGate 導入後は **意図的に注文しない** サイクルが存在する。

### 5.3 SkipGate 除外ベースの指標

skip_gate 86 件を分母から除外した「attempted (実際に発注した)」ベースの指標:

| 指標 | 全体ベース | attempted ベース (skip_gate 除外) |
|------|----------|--------------------------------|
| fill_rate | 67.5% (714/1057) | **73.5%** (714/971) |
| cancel_ratio | 32.5% (343/1057) | **26.5%** (257/971) |

attempted ベースでは cancel_ratio は E2 閾値 30% 以内だが、fill_rate は依然 90% に大きく届かない。

### 5.4 E1 fill_rate ≥ 90% の妥当性への疑問

fill_rate 90% は「板が十分厚い」ことの proxy として設定されたが:

1. **サイクル間隔 120s + timeout 300s** — 約 5 分間の注文機会ウィンドウで 90% 約定は、流動性が低い Coincheck BTC/JPY では非現実的
2. **time_filter による夜間スキップ** — 流動性の低い時間帯を既にフィルタしている上での 67.5%
3. **offset 戦略の影響** — 板の内側 (favorable) に置く注文は約定率が下がるのが自然

## 6. 提案: 二段階ゲート再設計

### 6.1 設計思想

| 原則 | 説明 |
|------|------|
| **早期棄却** | 72h の Kill Gate で明らかに破綻した戦略を早期に止め、時間的・金銭的ロスを最小化 |
| **段階的確認** | 168h の Qualification Gate でより厳密な品質基準を課す |
| **SkipGate 共存** | SkipGate スキップを分母から除外する新指標 (attempted ベース) を導入 |
| **000# §3.8 準拠** | Gate 枝番規則 (`.1`, `.2` 整数連番) に従い G1.1 / G1.2 と命名 |

### 6.2 G1.1-quick (72h Kill Gate)

**目的**: 明らかに不成立な戦略の早期棄却。  
**判定時点**: 72 時間経過 or n(attempted) ≥ 300、いずれか早い方。

| # | 指標 | 閾値 | 根拠 |
|---|------|------|------|
| Q1 | attempted_fill_rate | ≥ 60% | 継続中止ルール (000# §3.9) の 70% より緩く設定。Kill Gate は「明らかに不成立」の検出が目的 |
| Q2 | cancel_ratio (attempted) | ≤ 40% | Q1 の裏。パラメータ調整中の高キャンセルを許容 |
| Q3 | queue_wait_median | ≤ 120s | 300s timeout の半分。異常に遅い約定の検出 |
| Q4 | PnL30 (片側 t 検定) | p ≥ 0.01 | α=0.01 の強い有意でのみ Kill。α=0.05 より保守的 |
| Q5 | 累積実損 | < 10,000 JPY | 000# §3.9 キャップの維持 |

**FAIL 時**: fill_test 即時停止。戦略クラス変更 (aggressive maker, taker 併用) を検討。

### 6.3 G1.2-full (168h Qualification Gate)

**目的**: 完全な品質適格性の確認。  
**判定時点**: 168 時間 (7 暦日) 完了後。

| # | 指標 | 閾値 | 根拠 |
|---|------|------|------|
| F1 | attempted_fill_rate | ≥ 70% | 継続中止ルール (000# §3.9) と一致。attempted ベース |
| F2 | cancel_ratio (attempted) | ≤ 30% | 原初 E2 閾値を attempted ベースで維持 |
| F3 | queue_wait_median | ≤ 60s | 原初 E3 閾値を維持 |
| F4 | PnL30 (片側 t 検定) | p ≥ 0.05 | 原初 E4 閾値を維持 (有意に負でないこと) |
| F5 | AS_ratio | ≤ 35% | 原初 E5 (20%) から緩和。実測 31.4% を踏まえ、かつ SkipGate が AS 削減効果を発揮するはずの前提 |
| F6 | skip_gate_ratio | ≤ 20% | SkipGate がサイクルの過半をブロックしていないことの確認 |
| F7 | 暦日カバレッジ | ≥ 7 暦日 | 全曜日の市場特性をカバー |
| F8 | n (attempted) | ≥ 500 | 統計的検出力の保証 (MDE ≈ ±0.5 bps at 80% power) |

**FAIL 時**: 個別指標により対応分岐。
- F1/F2 FAIL → offset 戦略見直し or aggressive maker
- F4/F5 FAIL → SkipGate / sell_guard の再設計
- F6 FAIL → SkipGate 閾値の緩和

### 6.4 新旧対照表

| 旧 (G1.1 単一) | 新 (二段階) | 変更理由 |
|---------------|-----------|---------|
| fill_rate ≥ 90% (全体) | Q1 ≥ 60% / F1 ≥ 70% (attempted) | SkipGate 除外 + 閾値現実化 |
| cancel_ratio ≤ 30% (全体) | Q2 ≤ 40% / F2 ≤ 30% (attempted) | SkipGate 除外 |
| queue_wait ≤ 60s | Q3 ≤ 120s / F3 ≤ 60s | Kill は緩め |
| PnL30 p ≥ 0.05 | Q4 p ≥ 0.01 / F4 p ≥ 0.05 | Kill は「強い有意」のみ |
| AS_ratio ≤ 20% | (Kill に AS なし) / F5 ≤ 35% | 閾値緩和 + 72h 時点では不安定 |
| — | F6 skip_gate_ratio ≤ 20% | 新規: SkipGate 過剰スキップ監視 |
| — | F7 ≥ 7 暦日 | 新規: 曜日カバレッジ |
| — | F8 n ≥ 500 | 新規: 検出力保証 |

## 7. 統計的根拠

### 7.1 検出力分析 (Power Analysis)

| 時点 | n (fill) | CI half-width | MDE (80% power) | 十分性 |
|------|---------|---------------|-----------------|--------|
| 72h | 320 | ±0.54 bps | ±0.79 bps | △ 大きな効果は検出可能 |
| 96h | 430 | ±0.44 bps | ±0.64 bps | ○ 実用的 |
| 141h | 714 | ±0.39 bps | ±0.55 bps | ◎ 十分 |
| 168h (予測) | ~850 | ±0.36 bps | ±0.50 bps | ◎ わずかな追加精度 |

**MDE (Minimum Detectable Effect)**: 80% 検出力で検出可能な最小効果量。1 bps ≈ ¥1.47 のため、±0.5 bps の MDE は ±¥0.74/trade に相当。

### 7.2 CI 収束曲線

CI half-width は n=400 付近で 0.5 bps 以下に収束し、それ以降の追加は限界的:

```
n=100: ±1.8 bps
n=200: ±0.9 bps
n=300: ±0.6 bps  ← 72h 近辺
n=400: ±0.5 bps  ← CI < 1.0 bps (安定)
n=500: ±0.43 bps
n=700: ±0.39 bps ← 現在地
n=850: ±0.36 bps ← 168h 予測 (141h→168h で +0.03 bps の改善)
```

**結論**: 72h 時点 (n≈320) で大まかな判断は可能。168h まで待つことの追加精度は ±0.18 bps 程度。

### 7.3 レジーム / 曜日カバレッジ

| 面 | 72h 時点 | 141h 時点 |
|-----|---------|----------|
| 5 曜日 (月–金) | 3-4 曜日 | 全 7 日 (土日含む) |
| UTC 時間帯 | 16/24h | 24/24h |
| trending / ranging | 両方観測 | 両方十分 |

72h では週末データが欠落する場合があるため、F7 (≥7 暦日) は G1.2-full でのみ課す。

## 8. 72h 遡及検証結果

filltest の 141h データに対し、「72h 時点で Kill Gate があったら」をシミュレーション。

### 8.1 Q1-Q5 遡及判定

| # | 指標 | 72h 実測値 | Kill 閾値 | 判定 |
|---|------|----------|----------|------|
| Q1 | attempted_fill_rate | 69.8% | ≥ 60% | **PASS** |
| Q2 | cancel_ratio (attempted) | 30.2% | ≤ 40% | **PASS** |
| Q3 | queue_wait_median | 11.5s | ≤ 120s | **PASS** |
| Q4 | PnL30 p 値 (片側) | **0.015** | ≥ 0.01 | **PASS** (ギリギリ) |
| Q5 | 累積実損 | < 10,000 JPY | < 10,000 | **PASS** |

**Q4 は p=0.015 で Kill 閾値 (p ≥ 0.01) をギリギリ通過。** もし Kill 閾値が α=0.05 (原初 E4 と同じ) であれば FAIL だった。

### 8.2 遡及の示唆

- 72h Kill Gate に Q4 α=0.01 を採用したことは、この実データで正当化される
- PnL は 72h 時点で統計的に懸念があったが、141h で自然回復 (p=0.161)
- **α=0.05 で Kill すると、最終的に問題のない戦略を早期棄却するリスクがあった**
- 一方で **α=0.01 が甘すぎないか** — 真に損失を生む戦略を 72h で止められるかという懸念もある

## 9. リスクと懸念

### 9.1 提案に対する自己批判

| # | 懸念 | 深刻度 | 説明 |
|---|------|--------|------|
| C1 | **E1 fill_rate ≥ 90% → F1 ≥ 70% は大幅緩和** | ⭐⭐⭐ | 原初基準の「板が十分厚い」意図から 20pt 低下。これは基準の現実化か、敗北の合理化か? |
| C2 | **E5 AS_ratio ≤ 20% → F5 ≤ 35% も大幅緩和** | ⭐⭐⭐ | 約定の 1/3 が逆行して PASS とする妥当性。SkipGate が機能していれば AS は低下するはずでは? |
| C3 | **Q4 α=0.01 は甘すぎないか** | ⭐⭐ | 真に -1 bps の損失を生む戦略が 72h で n=320 あっても検出されないリスク |
| C4 | **attempted ベースは指標の粉飾か** | ⭐⭐ | skip_gate を除外するとあらゆる指標が改善する。SkipGate 自体の妥当性が十分検証されていない |
| C5 | **「大義」との整合** | ⭐⭐ | 000# §0「短期間での高収益性」— Gate 緩和は収益達成を容易にするものではなく、ただ Phase を進めやすくするだけ |

### 9.2 SkipGate の有効性問題

095# (Codex レビュー v3) で以下が報告されている:

> P0-1 SkipGate 動的較正: ✅ 実装・稼働中 → ❌ **効果なし** — P(AS) が AS/非 AS で同一分布

つまり **SkipGate は AS 予測精度が低い可能性がある**。にもかかわらず、SkipGate スキップ分を分母から除外する提案は、有効性が確認されていないフィルタの効果を前提としている。

### 9.3 survivorship bias の懸念

72h 時点で PnL が有意に負だったが 141h で回復した — これは:
- (A) param_adapter の学習効果 (offset が最適化された)
- (B) 市場レジームの変化 (trending → ranging)
- (C) 単なる平均回帰

(B) または (C) の場合、168h 完了後の G1.2 PASS も将来を保証しない。

## 10. レビューアへの質問事項

以下は優先度順。各項目に対し、**判断 (妥当/要修正/却下) + 根拠 + 代替案 (あれば)** の形式で回答を求む。

### Q10.1 [Critical] 二段階分割の設計原理

G1.1 (単一 168h) → G1.1-quick (72h Kill) + G1.2-full (168h Qualification) の分割は妥当か?

**具体的に**:
- Kill Gate の位置 (72h) は早すぎるか、遅すぎるか?
- Kill と Qualification の二段階で十分か、三段階 (e.g. 24h/72h/168h) にすべきか?
- 000# §3.8 の枝番規則 (`.1`, `.2`) との整合性は問題ないか?

### Q10.2 [Critical] 閾値設定の妥当性

特に以下の閾値について:

| 指標 | Kill (72h) | Full (168h) | 原初値 | 判断を求む |
|------|-----------|-------------|-------|----------|
| fill_rate | ≥ 60% | ≥ 70% | ≥ 90% | 90%→70% は過度な緩和か? |
| AS_ratio | (なし) | ≤ 35% | ≤ 20% | 20%→35% は妥当か? |
| PnL30 α | 0.01 | 0.05 | 0.05 | Kill での α=0.01 は適切か? |

### Q10.3 [High] SkipGate 除外 (attempted ベース) の統計的妥当性

- 「SkipGate スキップを分母から除外する」計算は acceptable か?
- SkipGate の有効性が未確認 (§9.2) の状態でこれを行う正当性は?
- 代替: skip_gate_ratio に上限 (F6) を設けるだけで、分母は全体のまま、という案はどうか?

### Q10.4 [High] 72h Kill 遡及検証の解釈

72h 時点で PnL p=0.015 (α=0.05 なら FAIL) → 141h で p=0.161 (回復)

- この回復は param_adapter の適応効果か、レジーム変化か?
- 「Kill しなくて正解だった」と解釈すべきか、「Kill すべきだった (現在の非有意は偶発)」と解釈すべきか?
- Q4 の α=0.01 は、この事例に基づくカーブフィッティングではないか?

### Q10.5 [Medium] 000# §3.3 を改訂する際の互換性

000# §3.3 の G1.1-exec を G1.1-quick + G1.2-full に書き換える場合:
- 009# (G1.1 実行計画) も同時改訂が必要か、archive で十分か?
- 014# §3 (Ph2→Ph3 移行条件) の「G1.1 PASS」を「G1.2 PASS」に読み替えるだけで足りるか?
- 既存の `fill_quality.py` の `g1_1_judgment()` はどう改修すべきか?

### Q10.6 [Medium] 見落としている観点

- この再設計で見落としているリスクや指標はあるか?
- 国際的な HFT/market-making の実務で、fill_rate 70% は妥当な水準か?
- BTC/JPY (Coincheck) の特殊性 (流動性、板の薄さ) を考慮した別の閾値設計があるか?
