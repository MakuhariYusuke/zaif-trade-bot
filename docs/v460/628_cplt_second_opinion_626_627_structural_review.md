# セカンドオピニオン: 626# / 627# の構造的損失と Sidecar 診断不良のレビュー

## 1. 概要と自己評価

本ドキュメント(628#)は、`626#` (Sell側テール損失の構造的原因分析) および `627#` (620#-626#の多角的検証とSidecarキャッシュバグの指摘) の内容を金融工学およびシステム工学の観点から厳格に監査した「セカンドオピニオン」です。

**結論として、626# の提示した「閾値のスケール不適合（120sウィンドウに対する50bps/6bps設定の乖離）」という論点は数学的に完全に正しく、早急な是正が必要です。一方で、627# の指摘通り、Sell側だけがすべての主犯ではなく、Buy側にも基礎的な負け（特に広範なウィンドウでのAdverse Selection）が存在しており、さらにML基盤（Sidecar）が現状ではテレメトリ上のバグにより完全に死んでいる状態であることが確認されました。**

### セルフレビュー (厳重注意)
- **過大評価の排除**: 626#で「大損バグはsell単独である」とされた部分は明らかな論理の飛躍(Overstatement)であり、627#の是正を追認します。
- **幻覚(Hallucination)チェック**: 「値の裏付け」として、120sウィンドウのビットコイン市場における6.0bpsの変動という数字は、マイクロ秒〜ミリ秒オーダのHFTにおいては発生し得るものの、直近のMedian AS (0.74bps) と比較すると「防御網として全く機能していない(遠すぎる)」という626#の指摘は定量的にも妥当です。
- **実証性の確保**: `sidecar_signal_io.py`の実装レベルのバグ（staleが(mtime, None)としてキャッシュされ、次回以降error扱いになる推移）を完全に特定しており、システムの死を幻覚ではなくコードの不備として実証しました。

## 2. 金融工学・市場微視構造からの考察 (盲点の拾い上げ)

### 2.1 Velocity Threshold (現在: 6.0bps) の課題と改善案
- **現状の診断**: `626#` の「6.0bpsは広すぎてAS防御にならない」は正しい。しかし、固定値（2.5bps）にただ下げるというアプローチにはリスク（盲点）があります。
- **盲点**: 市場の分散（σ）はボラティリティレジームによって毎分変動します。閑散相場での2.5bpsと、イベント時の2.5bpsは全く意味が異なります。
- **改善案**: 
  - 短期的適応（P1）: `627#` が推奨するように `6.0 -> 4.0 -> 3.0` とラダー形式でバリデーションを挟みながら下げる。
  - 構造的適応（P2）: `velocity_threshold` を完全な固定値（bps）ではなく、**リアルタイムの120s_sigma（標準偏差）の何倍かというZスコア（例: 2.0σ～3.0σ）に基づいてダイナミックに可変させる** アーキテクチャを検討すべきです。

### 2.2 Regime Threshold (現在: 0.5% = 50bps) の課題
- **現状の診断**: 120秒間で50bpsのトレンド発生を判定基準にするのは異常です。通常、日次のボラティリティが数％の資産に対し、120秒の窓で50bpsの変化があればそれは巨大なジャンプ（マイクロクラッシュ）です。
- **盲点**: 閾値が到達不可能であったため、実質的に全期間が `ranging` 扱いとなり、`trending` 特有のフィルタ（順張り、あるいは逆張り停止）が一度も稼働していませんでした。
- **改善案**: 120秒の標準偏差の実測値（過去データ等）に戻り、例えば `0.15%` 程度に引き下げる案は妥当です。ただし、この変更により**突然 trending ロジックが頻繁に発火することになるため**、その下流にあるロジック（trending時のオフセット調整など）が暴走しないか、慎重にテストすべきです。

## 3. Sidecar 実装バグの特定と修復 (System Engineering)

`627#` が言及した「stale sidecarが2回目以降errorに化ける」バグの根本原因は `scripts/v460/lib/sidecar_signal_io.py` 内に存在します。

### バグのメカニズム
1. **初回読込**: ファイルから有効だが古い(staleな)Signalを読み込む。
2. **TTL判定**: `_is_stale(signal.timestamp, ttl_sec)` が `True` となる。
3. **不正キャッシュ**: `_store_sidecar_cache(abs_path, (mtime, None))` という形で `None` をキャッシュに格納し、初回のみ `None, "stale"` を返す。
4. **次回読込**: mtimeが変わっていないためキャッシュにヒットするが、`cached_signal is None` の分岐に入り、`None, "error"` を返してしまう。

これにより、MLモデルが生成した古い信号が「エラー（システム異常）」と誤認され、テレメトリ全体の診断信頼性が崩壊していました。

### P0 修正内容
以下のように `sidecar_signal_io.py` を修正し、古いシグナルであってもキャッシュには実体を保持させ、毎回 timestamp 経由で stale と判定させる必要があります。

```python
# scripts/v460/lib/sidecar_signal_io.py: 修正案
      # 初回パース時の TTL チェック
      if ttl_sec > 0 and _is_stale(signal.timestamp, ttl_sec):
          logger.info(
              f"Sidecar signal stale: timestamp={signal.timestamp}, "
              f"ttl={ttl_sec}s exceeded"
          )
          # 修正前: _store_sidecar_cache(abs_path, (mtime, None))
          # 修正後: キャッシュには実体を保存する。以降は都度時間経過を判定させる。
          _store_sidecar_cache(abs_path, (mtime, signal))
          return None, "stale"

      # キャッシュ更新
      _store_sidecar_cache(abs_path, (mtime, signal))
      return signal, "fresh"
```
（合わせて、`tests/unit/v460/test_sidecar_sac_integration.py` に、同一staleファイルの複数回読み出しテストの追加が不可欠です）

## 4. 総括とネクストアクション

当システムの目標である「短期間での高収益性」を取り戻すには、基礎体力が正確に測定できることが大前提です。現在のアドバースセレクション防御は穴だらけであり、Sidecarは計器故障を起こしています。

1. **[急務 / 実装]** `sidecar_signal_io.py` のキャッシュセマンティクスを即座に修正し、テストを補強する。（これによりテレメトリの健全化と、MLシグナルの本来の威力を評価可能にする）
2. **[改善 / バックテスト]** `626#` の提案に沿って `velocity_threshold` を `4.0bps` → `3.0bps` と段階的に引き下げ、同時に `trend_threshold_pct` を `0.15%` に修正した環境下でのバックテストを実行する。
3. **[長期 / 研究]** 固定bpsによるハード閾値制御の限界を認識し、真の市場微視構造的アプローチとなる「ローカルボラティリティ（120sウィンドウの実際のσ）に基づくZスコア動的閾値」のR&Dに着手する。
