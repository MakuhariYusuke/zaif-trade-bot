## §2 重大指摘（新規発見）

## 2.1 `trades_health` イベント記録部の不整合

### 現象

- `run_fill_test.py` の `trades_health_alert` 生成で `th.latest_ts` / `th.age_hours` を参照している。
- しかし `TradesHealthResult` は `healthy / available_days / missing_days / stale_hours / message` のみ。
- 当該参照は `AttributeError` を誘発し、`except` に吸収されるため、**本来残るべき警告イベントが欠落**する恐れ。

### 影響

- retrain 品質劣化の監視証跡が不完全化。
- 「UNHEALTHY を検知したか」の運用検証が曖昧化。

### 優先度

- **P0（即修正）**

## §3 批判的レビュー（多角的視点）

## 3.1 収益性視点

- sell 側の「防御の螺旋」仮説は妥当。
- ただし offset 緩和は fill 改善と同時に adverse selection 増加を招くため、`fill_rate` 単独最適化は危険。
- 判定指標は最低でも `fill_rate / avg pnl30 / downside tail (p10 or worst decile)` の3点同時で管理すべき。

## 3.2 リスク管理視点

- P1-1 balance_forced 救済は必要だが、「救済モードの発火条件」と「解除条件」が曖昧だと損失固定化を招く。
- `Nサイクル連続 forced` + `ボラ閾値` + `最大救済時間` を必須にし、無限救済を禁止するべき。

## 3.3 ソフトウェア設計視点

- `run_fill_test.py` は分割が進んだ一方、行数増で依然高結合。
- ph2 稼働中は大規模分割より、`Facade維持 + 契約テスト先行` で段階移行する方が安全。

## 3.4 実験統制視点

- 158# の A/B 計画は有効だが、`variant` の系譜管理が弱い。
- `run_id -> config hash -> model hash -> git_sha` を1:1追跡できないと、後知恵分析が再現不能になる。

## §5 範囲外だが高効果の改善提案

## 5.1 実験ガバナンス強化（再現性）

- `results/v460/fill_test/manifest.jsonl` を導入し、各 run の `variant/model/config/git_sha` を自動記録。
- これにより「何が効いたか」の監査可能性を担保。

## 5.2 ダウンサイド監視の標準化（安全）

- 日次で `worst-10% pnl` と `連敗長` を可視化し、一定閾値で自動 `safe mode`。
- 平均値依存を避け、実運用での毀損を抑える。

## 追記: 158# / 159# に対するセカンドオピニオン (Gemini 3.1 Pro)

### 1. 159# (Codexレビュー) への評価と補足
159# の指摘（特に `trades_health` のバグ発見と、sell offset緩和に対するリスク警告）は極めて鋭く、実運用を強く意識した素晴らしいレビューである。優先順位の再編案（§4）も妥当であり、直ちに実行に移すべきである。

### 2. 見落とされている「致命的リスク」と「収益直結施策」

#### A. Oracleテスト (P0-4) の「結果評価」こそが真のP0である
159# では Oracle テストを「完了寄り」としているが、重要なのはスクリプトの存在ではなく**「その結果がどうだったか」**である。もし Oracle PnL（完全予測時の理論上限）から AS コストを引いた Net PnL がマイナスであれば、現在の Maker 戦略自体が破綻している（どんなに ML を改善しても勝てない）ことを意味する。他のいかなる改修よりも先に、Oracle テストの**結果評価と Go/No-Go 判断**を最優先で行うべきである。

#### B. sell offset 緩和 (P0-2) の代替案：非対称クオートと在庫偏重（Inventory Skewing）
159# でも警告されている通り、単なる sell offset の縮小は Adverse Selection の餌食になるだけである。収益に直結するアプローチとして、**「在庫状況に応じた非対称なクオート（Inventory Skewing）」**を提案する。
現状の `balance_forced` 救済（P1-1）は事後対応に過ぎない。在庫が一方に偏り始めた段階で、過剰な側の offset を広げ、不足している側の offset を狭める（あるいは同値撤退を許容する）ことで、在庫をニュートラルに保ちつつスプレッドを抜くマーケットメイカー本来の動きを実装すべきである。これを P0 に格上げすることを強く推奨する。

#### C. SkipGate sell 再訓練 (P0-1) 前の「構造的敗因」の特定
sell 側の PnL が極端に悪い原因を「旧データによるモデルの劣化」と決めつけるのは危険である。再訓練を盲目的に実行する前に、現在のモデルの**特徴量重要度（Feature Importance）と SHAP 値**を分析し、「なぜ sell 側だけが AS を回避できないのか」の構造的要因（例：マクロトレンドの影響、特定の特徴量のバグ）を特定するタスクを挟むべきである。

#### D. 「休むも相場」ロジックの欠如
158# のバックログには「エントリー条件の緩和」や「fill rate の向上」に関するタスクが多いが、高収益システムにおいて最も重要なのは**「期待値がマイナスの時に確実に取引を停止する」**ことである。133# で提案された「spread 狭小時の休む判定」や「worst hour-side の局所ルール学習」など、**防御的スキップロジックの精緻化**を P1 以上に組み込むべきである。

### 3. 結論とネクストアクション
159# の §4 (優先順位の再編) をベースとしつつ、以下の順序で実行することを推奨する。

1. **Day 0 (Go/No-Go)**: Oracle テストの結果を評価し、Maker 戦略の理論的優位性を証明する。
2. **Day 1 (観測修復)**: `trades_health` 不整合修正 (159# P0-A)。
3. **Day 2 (在庫管理)**: `balance_forced` の事後救済ではなく、事前予防としての Inventory Skewing ロジックの導入。
4. **Day 3 (分析と再訓練)**: sell 側モデルの SHAP 分析を実施した上で、SkipGate の再訓練 (158# P0-1) を行う。
