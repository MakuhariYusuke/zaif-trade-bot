# 536# 風水渙に基づくアーキテクチャ断捨離と統合の全体図（複数シナリオ）

- **日付**: 2026-03-22
- **目的**: 複雑化・パッチワーク化した現在のシステム全体の防衛機構およびパラメータ群を俯瞰し、「何を捨て（渙散）、何に纏め（廟に祭る）るか」の全体図を複数シナリオで提示する。
- **背景**: 易占「風水渙（ふうすいかん）」が示す「氷解・流動化（ポジティブ）」と「四散・統制喪失（ネガティブ）」の両義的解釈に基づく。

---

## §0 立筮の経緯と「風水渙 第三爻変」の解釈

本分析は、「12時・15時の帯域での売りのみ規制する」という時間帯ハードコード（≒弥縫策のパッチ当て）に対する疑義から出発しています。IF文による条件縛りばかりが増え、システムが硬直化して「二進も三進も行かない」状態に陥っていたため、局所的なパッチ当ての視野を脱し、全体を俯瞰する目的で乱数による略筮法（立筮）を行いました。

- **得られた卦**: **風水渙（ふうすいかん） / 変爻: 第三爻**
- **卦辞の解釈**: 「渙」は「氷解・散らす」の意。凍りついた水（硬直化した固定値や事後対応ルール）に春の風を通して、再び流動化させるべき時を示します。これは「時間帯などの固定値にこだわるのをやめ、動的な微視的構造へ移行せよ」という金融工学的要請と見事に合致します。
- **第三爻変の解釈**: **「其の躬（み）を渙（ち）らす。悔いなし。」**
  - **金融工学/ML理論的意味**: 「躬（み）」とは自分自身の執着やエゴを指します。開発者が陥りがちな「この時間帯が怪しいから止める」という過学習（Overfitting）や、理解しやすいが脆い「固定ルール」への執着を手放すことを促しています。次元の呪いを招く「MLへの全委譲」のような無秩序な四散を戒めつつ、OFI等の普遍的で本質的な特徴量（ハブ）に次元圧縮・統合することで、システムは後悔のない堅牢さを手に入れます。

## §1 易占「風水渙」から導くアーキテクチャ原則

卦辞に曰く、「渙。亨。王格有廟（王、有廟に至る）。利渉大川（大川を渉るに利ろし）」。

1. **氷を溶かす（Market Microstructureの導入）**: 相場が変われば腐る「物理時間（12h/15h）」や「固定閾値（700 JPY）」「遅行型のKill」は、市場の流動性に対する硬直した氷です。これを解き放ち、情報の非対称性（PIN/VPIN）やオーダーフローの不均衡（OFI）などの「市場の風（ダイナミクス）」を用いた動的指標に変える時期です。
2. **大川を渉る（根本的リファクタリングの好機）**: 小手先のパッチ（弥縫策）を当てるのではなく、アーキテクチャの骨格（予測型指標による一元防衛への移行）に手を入れる大きな変更が吉。
3. **王、有廟に至る（統制の核を忘れない）**: 全てを散らして（MLに丸投げするなどして）統制を失えば、過去の「パラメータ発散の失敗」の二の舞になります。必ず「絶対にブレない神髄（廟＝最終防波堤・コアコンセプト）」だけは強固に残さねばなりません。

## §2 現在のシステム・パラメータ構造の俯瞰（どこが詰まっているか）

現在、コードとYAMLには主に以下の3レイヤーの「防衛・調整機構」が混在・干渉し、**一部で切り捨て（Ceiling等）が発生し上流が無駄**になっています。

| レイヤー | 該当機能（現状） | 問題点・状態 |
|---------|-----------------|-------------|
| **1. 実行前ゲート (Gate/Veto)** | `cross_venue_lead_lag_veto`<br>`min_spread_jpy`<br>`balance_insufficient` | 「デッドロック（死場）」の根本原因。環境変動への適応性がない固定値による過剰防衛が発生。 |
| **2. オフセット演算 (Pipeline)** | `base` -> `as_shift` -> `regime` -> `spread_adapt` -> `vol_guard` -> `final`<br>**`max_offset_ceiling (0.25)`** | 層が多すぎる上、足し算と掛け算が混在。結果的に **`ceiling` で丸められ（100%飽和、531#参照）、上流の重み付け計算が取引執行に全く反映されていない。** |
| **3. 事後対応ガード (Kill/Skip)** | `sell_dynamic_kill`<br>`trending_sell_skip` | 損失（ドローダウン）を被弾してから発動する「遅行指標」。防衛ではなくサンドバッグ。 |

## §3 全体図と再構築のシナリオ（3本線）

事態を「渙（と）かす」ためのアプローチとして、リスクと効果に応じた3つのシナリオを提案します。

### シナリオ A: 抜本的ハブ化（大川を渉る案） — おすすめ
**「予測的（Predictive）シグナルであるOFIに防衛機能を束ねる」**

- **散らす（捨てる）**: `sell_dynamic_kill`, 時間帯条件, 固定値 `min_spread_jpy` (700等), オフセット乗算の冗長な段。
- **束ねる（廟に祭る）**: 
  - **Toxic/Adverse Selection (AS) 防衛ハブ** ＝ `OFI (Order Flow Imbalance)` + `CV (Cross-Venue) 先行シグナル`。
  - **具体案の深掘り**:
    - `ofi = (bid_vol_diff - ask_vol_diff) / total_vol` を計算し、`ofi < -0.8` (強いToxic Sell圧力) を検知した場合、従来のようにKillするのではなく、**`min_spread_jpy` を動的に拡張 (例: `base_spread + abs(ofi) * penalty_factor`) し、逆選択のコストをスプレッドに内部化する**。
    - 防衛は「事後のPnL（売って負けた）」からではなく、この「ハブによる事前予測」のみで行う。
- **Ceilingの廃止と動的化**: `ceiling` という固定の蓋を撤廃し、ベーススプレッド自体を「ATR（直近ボラティリティ）」の係数として動的に設定（例: `ATR * 0.5`）。
- **評価**: 金融工学的な正しいアプローチ（情報の非対称性の価格転嫁）であり、過学習を排除できる。コードは極めて美しくなる。

### シナリオ B: パイプライン正規化案（内部配管の修繕案）
**「捨てすぎ（四散）を恐れ、機能の干渉・切り捨てだけを正す」**

- **散らす（捨てる）**: `ceiling` による強制丸め処理。
- **束ねる（廟に祭る）**: 
  - 多層の Offset Pipeline （AS, Regime, Spread）をそのまま使わず、「各指標を Sigmoid 関数等で 0.0 〜 1.0 に正規化したスコア」へ変更。
  - **具体案の深掘り**:
    - `Total Score = w1*AS_score + w2*Regime_score + w3*Spread_score` のように加重平均(Logit)をとり、最終的に `Base Offset × (1.0 + Total Score)` （最大2.0倍などでキャップ）する形に集約。
    - これにより、どこか一つの極端な値（外れ値）で他が潰される（あるいはCeilingを突き抜ける）事故を防ぐ。
- **評価**: 現状のパラメーターの多くを残しつつ、隠れた「無駄（切り捨て）」をなくす。ただし `sell_dynamic_kill` 等の事後対応による遅行性はそのまま残る。

### シナリオ C: 枯死機能の単なる剪定（安全第一案）
**「まずは明らかな不要物だけを風に飛ばす」**

- **散らす（捨てる）**: 
  1. 常に係数が1.0となっている、あるいはCeilingで潰されて無意味化している Offset段の単なる削除。
  2. 実質的に無意味であるばかりか、Veto後のリカバリーを阻害している `sell_dynamic_kill` をオミットする。
- **追加パッチ**: 532#で指摘された「Inventory=0時のVeto緩和（時間減衰）」のみを追加する。
- **評価**: 実施コストが異常に低く、副作用（四散のリスク）がない。ただし根本的な「ハードコード過学習体質」の解決にはならない。

## §3 今後のアクション決定に向けて

「MLによる全パラメーターの学習」は、過去の知見の通り**「廟（明確な設計思想）」を持たない無秩序な渙散（四散）**であったために発散したのだと考えられます。
したがって、今やるべきはMLに逃げることでも、逆に固定のIF文（12時だから止める、等）に頼ることでもありません。

**【提案】**
まずは**シナリオA（抜本的ハブ化）**を最終目標（To-Be）として見据えつつ、**直近の実装としてはシナリオCから入り、Ceilingの飽和や事後Killの廃止（ゴミ掃除）を実施する**、というグラデーションでの対処はいかがでしょうか。

これにより、IDEのコンテキストを無駄に消費せず、全体の「見通し（風通し）」を良くすることができます。どの線（A, B, C）を軸に設計を進めるか、ご意見を伺えれば幸いです。
