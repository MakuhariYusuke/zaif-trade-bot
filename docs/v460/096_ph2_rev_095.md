## §3 095 の Q1-Q6 への回答

### Q1 SkipGate 根本改善

1. 主因は `C=0.01` 単体ではなく、**feature contract 崩壊** と **閾値運用不全**。  
2. ラベル定義もズレがある。学習は `adverse_selected_raw`、運用評価は deadzone 適用 AS を主に見ており、設計思想が不一致。  
3. まずはルールベース fallback（危険時間帯 + spread/wait 条件）を併用しつつ、ML を再学習するのが現実的。  
4. 再利用候補は `070` の候補モデル群。特に「注文前に取れる特徴量のみ」で再学習した candidate を先に A/B する。

### Q2 Offset 最適化

1. 目的関数は `fill_rate` と `AS` ではなく、`期待PnL/サイクル` に置くべき。  
2. side 別で探索する。buy は `0.05/0.075/0.10`、sell は `0.12/0.16/0.20/0.24` の小規模グリッドを推奨。  
3. 適応は全履歴ではなく rolling window（例: 直近120 clean）で判定する。

### Q3 Fast Fill Defense / Adapter 状態管理

1. `base_offset + temp_boost_multiplier` 分離は妥当。  
2. 実行順は「base更新（低頻度）→ 注文前に multiplier 適用（高頻度）」で固定する。  
3. 同時稼働は可能。ただし「同じ変数を直接書き換える実装」は禁止。

### Q4 10-30s Wait Band

1. informed trader テイク仮説は妥当だが、因果断定はまだ不可。  
2. 次サイクル反映より、当該サイクル内の早期 cancel-requote を優先すべき。  
3. Coincheck の構造傾向はあり得るため、wait 帯を KPI として常時監視し、side 別に制御する。

### Q5 Sell 平均回帰の活用

1. 最新45件の 120s データでも sell は `+0.999bps`、buy は `-0.688bps`。sell に平均回帰傾向は残る。  
2. sell の 30s 負け13件では、120s で平均 `+1.629bps` 改善。一定条件下で保持延長は有効。  
3. ただし tail 管理は必須。`max_hold=120s` と `-8bps` 緊急切りを併設する。

### Q6 全体アーキテクチャ

1. offset 8段チェーンは複雑化し過ぎ。現在は相互作用の追跡コストが高い。  
2. `spread × ratio` 単独では不十分。最低限 `spread`, `flow`, `volatility`, `session` の4軸で設計し直すべき。  
3. `cycle_interval=120s` は当面維持でよい。先に SkipGate/状態競合/timeout を直す方が効果が大きい。  
4. 最優先は `M1 SkipGate再建` と `M2 状態分離` の2点。
