## 0. 総括

3文書のうち、**一番バランスが良いのは 562#** である。560# は実データに強く、561# は理論駆動で切れ味があるが、どちらもやや片寄りがある。560# は「sell 側 AS」を強く押し出す一方で **buy 側の悪化を相対的に軽く扱い過ぎている**。561# は「固定 Ceiling が悪い」という問題意識はよいが、**既存実装との重複と母集団の不純さ**をまだ十分に処理できていない。

したがって、現時点の妥当な立場は次の通りである。

1. 560# の統計観察は有益。ただし、そのまま施策へ飛ばず、**same-SHA / same-config の再分解**が先。
2. 561# の DRC 発想は有望。ただし、新レイヤ追加ではなく、**既存の ceiling / OFI / hour boost の統合再設計**として詰めるべき。
3. 562# の統合作業は方向として最も正しい。ただし、**「売り側だけが本丸」という整理はまだ強過ぎる**。

## 2. 560# への評価

### 2.1 支持できる点

- `AS -7.24 bps` と `Non-AS +2.31 bps` の分解は非常に有益である。ここは本システムの損益構造を端的に示している。
- JST 22-23 時のテール過大表現抽出は価値が高い。時間帯リスクを感覚ではなく分布で示している。
- `clamped` と `unclamped` の差を切った点もよい。ceiling が単なる安全装置でなく、**期待値そのものを潰している可能性**を見せている。

### 2.2 反論・補強が必要な点

#### A. sell 側主犯論が強すぎる

560# の narrative は sell 側 AS を主犯に置いているが、自身の数値を見ると、平均損益はむしろ buy の方が悪い。さらに最悪約定も buy 偏重である。したがって、560# は次のように補正した方がよい。

- **sell**: 高 AS・厚い左尾・時間帯依存が強い
- **buy**: 平均損益が悪く、巨大損失が混じる

つまり、構図は「sell だけ壊れている」ではなく、**sell は尾が太く、buy は平均が沈んでいる**である。

#### B. 現行設定とのズレを本文で明示すべき

560# の期間には旧設定が混ざる可能性が高い一方、読み手は現在の `configs/v460/fill_test.yaml` と混同しやすい。特に次は明記が必要である。

- 現行 `offset_ceiling_ratio_buy/sell` は `0.30`
- `hour_ceiling_mult` は実装済み
- 現行 `sell_dynamic_kill_enabled` は `False`
- `composite_risk_enabled=true`, `threshold=1.0`

ここを書かないと、「未対策の問題」と「対策済みだが効いていない問題」が混ざる。

#### C. 参加制約の重さをもっと前に出すべき

560# は AS を強く扱う一方で、cancel reason を見ると `preflight_insufficient`, `spread_too_narrow`, `skip_gate` も大きい。これは市場理論上、「毒を避ける」だけでなく、**良い局面に参加できていない**可能性を示す。収益最大化の観点では、

- 守り過ぎて機会を失っているのか
- 参加したときだけ毒を踏んでいるのか

を分ける必要がある。560# は前者の掘り下げがまだ薄い。

## 3. 561# への評価

### 3.1 支持できる点

- 「巨大ペナルティで教育するより、執行エンジンの生存圏を先に制御する」という立場は妥当である。
- Glosten-Milgrom 的な観点から、必要スプレッドや retreat distance が市場状態に応じて変わるという主張も正しい。
- `追従遅れの罠`, `Action Space の歪み`, `母集団の不一致` を自分で論点化しているのも良い。問題意識は鋭い。

### 3.2 反論・補強が必要な点

#### A. 「固定 Ceiling が本質」は強すぎる

561# は fixed ceiling mismatch を中心原因に置くが、fill test の不調はそれだけでは説明し切れない。現実には、

- preflight / inventory 制約
- spread too narrow
- gate block
- sidecar 死亡期間
- mixed regime / mixed config

が重なっている。金融工学的にも、収益低下を単一パラメータで説明し切る局面ではない。

#### B. 低相関 = 静的フィルタ無効、とは限らない

`Spread, Imbalance, VPIN と AS の相関が低い` ことから `静的フィルタでは防げない` と論じているが、これは統計的には飛躍がある。

考えられる代替解釈は次の通り。

1. 単変量では効かず、**交互作用**で効いている
2. mixed regime が相関を希釈している
3. そもそも指標の計測粒度が粗く、**本来の毒性を取り切れていない**
4. 既存ガードがすでに一部を除去しており、観測された母集団が歪んでいる

よって、「静的閾値を捨てる」ではなく、「単変量閾値だけでは弱い」が妥当である。

#### C. DRC は新機構として増やすより、既存制御の統合先として定義すべき

561# の DRC 発想自体は悪くない。ただし、そのまま別レイヤとして足すと、現在すでにある

- `offset_ceiling_ratio_*`
- `hour_ceiling_mult`
- OFI 由来の multiplier
- δ* 由来の dynamic ceiling

と重なり、また ceiling 飽和の別名になる危険がある。したがって DRC をやるなら、

- `resolve_offset_ceiling()` 系の**単一責務化**
- side ごとの adverse direction の符号規約統一
- `spread_bps` 分母 floor
- hard cap の最終位置固定

まで含めて、**「新しい数式」ではなく「制御トポロジの整理」**として出すべきである。

#### D. sell に寄り過ぎている

561# は sell の左尾に集中しているが、560# の窓では buy 側も平均損益で負けている。したがって 561# が本当に強くなるには、「sell-tail DRC」を超えて、

- buy に対してはどの条件で同様の動的 retreat が必要か
- あるいは buy は retreat より participation 改善が主か

まで書いた方がよい。

## 4. 562# への評価

### 4.1 支持できる点

- 560# と 561# を「データ担当」と「理論担当」に分けて宿題化したのは非常に良い。
- 既に実装済みの項目を明確に棚卸ししており、重複提案をかなり抑制できている。
- 「防衛の二重計上」問題の言語化も鋭い。現行 fill 系の悩ましさをよく表している。

### 4.2 補強が必要な点

#### A. mixed-SHA / mixed-config の警告をもっと前面に出すべき

562# は現在地との照合ができているが、560#/561# の母集団純度の問題をまだやや穏当処理し過ぎている。ここは遠慮せず、

- この集計は current-state の因果判定には使い切れない
- まず same-SHA / same-run / same-config 分解が先

と書いてよい。

#### B. AS Risk Score の結合則はまだ未決着

`max()` は美しいが、情報を捨てる。逆に加算は危険。よって 562# の一元化案は支持するが、結合則は次の 3 候補を並べて小さく比較した方がよい。

1. `max()`
2. `sqrt(sum(w_i * s_i^2))` 型の RMS
3. `min(cap, sum(w_i * s_i))` 型の capped sum

ここは設計論として重要で、いきなり `max()` に確定しない方が良い。

#### C. side-specific knobs を増やす前に、既存 knobs の寄与分解が必要

562# は `cross_venue_favorable_tighten_sell_enabled` のような side-specific knob を提案しているが、いまの fill 系は既にノブが多い。設計面では、追加前に

- 実際にどの条件で favorable tighten が効いているか
- sell 側 no-op / cap-hit 率はどの程度か
- same-SHA で効能差があるか

を出してからでも遅くない。

## 5. 三者が見落としている盲点

### 5.1 「毒を避ける」より「良い局面に参加できていない」問題

3文書とも AS 防衛に比重が寄っているが、収益最大化の観点では、**良い局面を逃している損失**も同じくらい重い。`preflight_insufficient`, `spread_too_narrow`, `skip_gate` が大きいなら、問題は「毒を踏むこと」だけでなく「参加率の質」でもある。

### 5.2 sell-only narrative に引っ張られ過ぎている

sell 側の左尾は確かに重いが、buy 側は平均損益の悪化と巨大負けが問題である。したがって、

- sell: tail risk 防衛
- buy: mean recovery / participation quality 改善

という**非対称の処方箋**が必要である。

### 5.3 ceiling を上げれば自然に良くなる、とは限らない

clamp 飽和は重要だが、上流の multiplier が過大なままなら、ceiling を上げても「より深く逃げるだけ」で fill rate や毒性構造が別の形で悪化する。ゆえに ceiling 引上げは、**上流 multiplier の整理とセット**で見るべきである。

### 5.4 SAC/sidecar が死んでいた期間の交絡

560# の期間では sidecar 死亡や再起動影響が混ざる可能性がある。ここを明示しないと、「市場が悪い」のか「補助制御が消えていた」のかが混ざる。

## 7. 結論

560# は**観測として有益**、561# は**仮説として鋭い**、562# は**統合作業として最も健全**である。したがって次にやるべきことは、新しい思想をさらに足すことではない。順番は次の通りでよい。

1. 560著者が母集団を浄化し、観測を same-SHA 化する
2. 561著者が DRC を「新ノブ」ではなく「既存 ceiling 系の統合仕様」に書き直す
3. 562著者が buy/sell 非対称性も含めて execution topology を一本化する

この順なら、議論が増えるだけで実装が硬直する状態をかなり避けられる。逆に、560/561 の不純な母集団のまま新機構を追加すると、また attribution が壊れる可能性が高い。
