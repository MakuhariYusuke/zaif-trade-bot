## §0 総評（結論）

§7 は「G0→G1→G1.1→G2→G3→G4」の順序設計自体は妥当で、v459 の反省（情報量検証の前倒し）を正しく反映できています。  
ただし、現状のまま着手すると **実装段階で詰まる仕様不整合** が複数あります。

特に以下 6 点は、着手前に 001 を修正しないと高確率で遅延します。

1. 章番号の構造不整合（§7 の後に §6 が出現）
2. HFT志向と収集粒度（REST/1分集約）の不一致
3. `IBroker` 拡張時の破壊的変更リスクの過小評価
4. async 設計なのに adapter 実装が同期 `requests` 依存
5. `DataScheduler` 流用前提の不一致（実体は Binance 専用実装）
6. G1 判定ロジック（Holm + p-mean AND）の実装仕様が曖昧

## §2 §7 実装ロードマップの妥当性判定

### 2.1 正しい方向性（維持推奨）

- Gate順序（G1を前段化）は妥当。`docs/v460/000_ph0_plan_project_proposal.md:91`
- 既存資産の流用方針（`run_manifest.py`, `hft_proxies.py`, `ExchangeFeeModel`）は正しい。
- `run_experiment.py` を唯一ランナーに寄せる設計は、運用統制上は有効。

### 2.2 そのままでは危険な点（修正必須）

- `P0-1` の 0.5d 見積は楽観的。`IBroker` 変更は adapter + sim + tests 波及を含む。`docs/v460/001_ph0_plan_technical_specs.md:431`
- `P0-4` が Coincheck 前提で、Bitflyer分岐と依存の整合が弱い。`docs/v460/001_ph0_plan_technical_specs.md:434`
- HFT志向に対して REST 1分収集中心は情報劣化が大きい。

## §3 見落とし事項（追加指摘）

1. `p_mean_method` が `ztb/metrics/metrics.py` 内で重複定義されている。  
`ztb/metrics/metrics.py:1394`, `ztb/metrics/metrics.py:2069`  
Gate 実装時にどちらを参照するか曖昧になるため、関数を一本化すべき。

2. 取引所シンボル表記が混在（`btc_jpy` / `BTC_JPY`）。  
`ztb/trading/live/exchanges/coincheck/adapter.py:88`, `ztb/trading/live/exchanges/bitflyer/adapter.py:70`  
collector・evaluator 間で結合失敗を起こしやすい。

3. `PaperTrader` は現状、再生データを合成生成する経路が残っている。  
`ztb/trading/live/simulation/paper_trader.py:150`  
G4 実運用近似の検証基盤としては不十分なため、market replay 実データ固定が必要。

4. `run_experiment.py` を 200 行以内に固定する目標は、将来の task 増加で破綻しやすい。  
`docs/v460/001_ph0_plan_technical_specs.md:226`  
行数制約より責務境界（orchestrator 専任）を仕様化する方が有効。

## §6 最終判定

第7章の方向性は「間違い」ではありません。  
ただし、現状は **実装互換性と判定仕様の曖昧さ** が残っており、ここを放置すると v459 と同じく「実験は回るが結論が揺れる」状態に戻ります。

v460 を強くするための最短ルートは以下です。

1. 章構造修正（§6/§7の整合）
2. G1 判定アルゴリズムの厳密仕様化
3. `IBroker` 拡張の段階移行設計（互換レイヤ）
4. tick raw 収集を前提にしたデータ契約の再定義
