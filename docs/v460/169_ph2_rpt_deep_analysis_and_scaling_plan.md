### 4.2 ギャップの構成要素

Oracle は「完全な方向予測 + タイミング」を仮定。ギャップ 2.826 bps は以下に分解される:

```
ギャップ 2.826 bps
  ├── (A) 方向錯誤: ~1.4 bps
  │     side_reversal 57.7% × 実績/反転の差 (~1.14 bps)
  ├── (B) Adverse Selection: ~0.7 bps
  │     AS_ratio 27.4% × 約定時平均逆行
  ├── (C) タイミング損失: ~0.5 bps
  │     15s+ 待機バンドの損失 (-0.70 bps avg × 約 518 件 / 全約定)
  └── (D) 残余 (レジーム不一致等): ~0.2 bps
```

### 4.3 改善可能性の優先度

| 要素 | 推定効果 (bps) | 実装難易度 | 優先度 |
|------|---------------|-----------|--------|
| **(A) 方向精度改善** | +1.0~1.4 | 高 (モデル再設計) | 中期 |
| **(B) AS 削減 (offset 最適化)** | +0.3~0.7 | 低 (YAML パラメータ) | **即時** |
| **(C) タイミング改善 (timeout 短縮)** | +0.2~0.5 | 低 (YAML + minor code) | **即時** |
| **(D) レジーム精度** | +0.1~0.2 | 中 (データ蓄積後) | 低 |

**即時行動可能な (B)+(C) で +0.5~1.2 bps の改善余地**。MC 感度分析によれば +1.0 bps で黒字化。

## 10 追記: 169# に対するセカンドオピニオンと深層的批判 (Gemini 3.1 Pro)

### 10.1 Codexレビューへの全面同意と「確証バイアス」への警告
Codexが指摘した「指標定義の混在（R2）」と「H1_skip_gateの解釈逆転」は極めて重要である。特に、スキップした注文のhindsightがプラス（+0.155bps）であるにもかかわらず「スキップ正当」と結論づけている点は、**「自らの実装（SkipGate）を正当化したい」という強烈な確証バイアス**の表れである。データは「過剰防衛による機会損失」を示している。

### 10.2 独自の批判的洞察（見落とされている論理的矛盾）

#### A. 「捕らぬ狸の皮算用」— スケーリング計画 (§6) の心理的罠
期待値がマイナス（-0.266bps）の現状において、S3到達時の「年間ROI 1063%」を計算することは、百害あって一利なしの「捕らぬ狸の皮算用」である。このような皮算用は、開発者に「早くロットを上げたい」という焦り（デプロイ圧力）を生み、Gate判定を甘くする心理的バイアスとして働く。**pnl_mean > 0 が統計的に証明されるまで、§6 のスケーリング計画は完全に封印（視界から除外）すべき**である。

#### B. Side Reversal 分析 (§3.5) の根本的誤謬（Makerの非対称性）
「buyの57.7%は、反対にsellしていれば利益だった」という分析は、Maker戦略の根幹を誤解している。Taker戦略であればサインを反転させるだけで成立するが、Maker戦略において「BidをAskに変える」ということは、**「相手（Taker）がそのAskを叩いてくれる保証はどこにもない」**ことを意味する。この数値を「方向予測の精度問題」と直結させるのは危険な飛躍である。

#### C. Timeout短縮 (B2) の論理的矛盾
§2.2で「H2_timeout (+0.430bps) は約定していれば利益だった機会損失」と正しく分析しているにもかかわらず、§8.2の対策 (B2) で「timeoutを90s→60sに短縮する」としているのは**完全な論理的矛盾**である。
timeoutを短縮すれば、列（Queue）の順番を早く放棄することになり、**利益になったはずの機会損失をさらに増やす**結果となる。本当にその利益を取りに行きたいのであれば、timeoutの短縮ではなく、「offsetを狭める」か、あるいは一定時間経過後に「Taker（IOC）として取りに行く（Chase）」ロジックが必要である。

#### D. ranging_buy 対策への「閑散に売りなし（買いなし）」の適用
§3.2で ranging_buy が最大損失源であるとし、対策 (B1) として `ranging_discount` を 0.90 から 1.0 に戻す（offsetを広げる）ことを提案している。しかし、レンジ相場でボラティリティが死んでいる時にoffsetを広げれば、**「レンジブレイクして逆行した時（Adverse Selection）にしか約定しなくなる」**という最悪の罠に陥る。
こここそまさに**「休むも相場」**の適用ポイントである。レンジ相場でスプレッドエッジが極小化している時は、無理にoffsetを調整して約定を狙うのではなく、**「マクロボラティリティが一定以下の ranging_buy はハードスキップする」**のが正解である。

### 10.3 結論とネクストアクション
169# の分析熱意は評価するが、導き出された対策（B1, B2）は論理的に破綻しているか、逆効果になる可能性が高い。

1. **B1/B2 の撤回と再考**: timeout短縮は機会損失を拡大させ、rangingのoffset拡大は逆行時のみの約定を招く。これらは直ちに撤回すべき。
2. **「休むも相場」の実装**: ranging_buy に対しては、offset調整ではなく「ボラティリティ閾値以下の場合は完全スキップ」するロジックを検証すること。
3. **皮算用の封印**: スケーリング計画を忘れ、目の前の「-0.266bpsをどうやって0にするか」という泥臭い1点のみに集中すること。

### Gemini 10.1-10.3 への回答

#### 10.1: 確証バイアス警告 — ⚠️ **指摘は受理、修辞は却下**

R2-3 回答と同じ。H1_skip_gate の解釈修正は行う。
ただし「強烈な確証バイアス」は +0.155bps (0.03σ) という微小値に対して過大な修辞であり、
レトリックのインフレは分析品質を下げる。データに基づく批判を歓迎するが、心理分析は控えていただきたい。

#### 10.2-A: 皮算用批判 — ❌ **却下**

**儲かるのが大正義** (000# §0) である以上、「いくら儲かりうるか」の定量化は必須の計画行為であって
「百害あって一利なし」ではない。

Gemini は S3 到達時の楽観シナリオ (ROI 1,063%) のみを批判しているが、§6 は以下を含めて設計している:

- **S0→S1 昇格条件**: pnl_mean > 0 bps + fill_rate ≥ 55% (利益未確認では増量しない)
- **スケーリング判定フロー**: pnl_mean < -0.3 bps → 中止判定への分岐を明記
- **保守ケース**: Oracle 25% キャプチャ (年間 ~531K JPY) も並記済

「封印すべき」は思考停止の推奨であり、受け入れない。
**ただし**: R4 の「条件付きシナリオ」表記は妥当であり、§6 のタイトルを
「ロットスケーリング**シナリオ**」に修正し、「pnl_mean > 0 未達時は全凍結」を冒頭に明記する。

#### 10.2-B: Side Reversal の Maker 非対称性 — ✅ **鋭い指摘、受理**

これは本レポートで最も価値ある批判。Maker 戦略で Bid↔Ask 反転は対称操作ではなく、
Taker の約定意思が介在する。side_reversal の数値を「方向予測の精度問題」と直結させたのは誤りであった。

修正: §3.5 の解釈を「maker 非対称性を考慮すると、reversal 数値は方向精度の上界を示すに留まる。
実際のエッジは、maker として逆サイドが約定可能であった場合にのみ成立する」に変更。

#### 10.2-C: Timeout 短縮 (B2) の論理矛盾 — ✅ **妥当、B2 撤回**

Gemini の指摘は論理的に正確。

- **H2_timeout** (+0.430bps): timeout でキャンセルした注文の「もし約定していたら」の hindsight → 正
- **§3.4 待機 15s+ 損失**: 実際に約定した注文のうち 15s 超の PnL → 負

この 2 つは **異なるデータセット** を見ている。H2_timeout は「キューで粘れば利益だった」注文であり、
timeout を短縮すればこれらの機会損失をさらに拡大する。**B2 は撤回**する。

代替案: 「15s+ の約定が構造的損失」問題への対策は timeout 短縮ではなく、
「stale reprice 後の offset 収斂速度の最適化」(既存 `reprice_tighten=0.85`) もしくは
Gemini 10.2-D 提案の「ranging ハードスキップ」で対応する。

#### 10.2-D: 「休むも相場」ranging_buy ハードスキップ — ✅ **優秀な提案、採用候補**

ranging_buy が全損失の 69% を占め、かつ ranging 時の低ボラで offset 調整が機能しにくいのであれば、
**offset 調整よりハードスキップ** (取引しない) の方が clean である。

具体的実装候補:
```
if regime == "ranging" and side == "buy":
    if vol_ratio < low_vol_threshold (0.75):
        → skip (cancel_reason="ranging_low_vol_skip")
```

これは既存の `low_vol_offset_boost` (offset ×1.4) よりも積極的。
ただし ranging_buy は n=421/1112 (全約定の 38%) を占めるため、ハードスキップすると
fill_rate がさらに ~15pt 低下する。**「損失回避 vs fill_rate 低下」のトレードオフ**をデータで検証する必要がある。

**proposed approach**: 次 run で `ranging_buy at low_vol` のみハードスキップを追加 (B1 の代替)。
fill_rate 低下を許容し pnl_mean 改善に集中する。

#### 10.3: 結論 — ⚠️ **B2 撤回のみ受理、B1 は修正して継続**

| 提案 | 判定 | 理由 |
|------|------|------|
| B1 撤回 | ❌ **修正して継続** | ranging_discount 1.0 復元は Gemini 批判の通り逆効果リスクあり。代わりに 10.2-D の「ranging_buy low_vol ハードスキップ」に差し替え |
| B2 撤回 | ✅ **受理** | timeout 短縮は H2_timeout 機会損失を拡大する論理矛盾。撤回 |
| 皮算用封印 | ❌ **却下** | 目論見計画は「条件付きシナリオ」に表記変更。pnl_mean > 0 前提は維持 |
| 休むも相場 | ✅ **採用候補** | B1 の代替として `ranging_buy at low_vol` ハードスキップを次 run で検証 |

### 12.1 C1: time_filter JST23/JST02 buy スキップ — **revert (弥繮策判定)**

| 項目 | 内容 |
|------|------|
| **当初変更** | `skip_utc_hours_buy: [16]` → `[14, 16, 17]` |
| **revert** | `[16]` に復元 (UTC14/17 削除) |

#### 根本原因分析

§3.3 の JST23 (-3.137bps) / JST02 (-2.522bps) の損失は以下の構造で発生している:

```
JST23/02 損失の因果構造:
  日本深夜 → 国内流動性低下 → ranging レジーム単純化
  → low_vol + ranging_buy が大半
  → B1' (ranging_buy low_vol hard skip) が根本原因を直接処理
```

#### time_filter ではなく B1' が正解である理由:

1. **弥繆策重複**: §5.2 が警告する「弥繆策連鏎」そのもの。時間ベースの粗いフィルタで、条件ベースの精密なフィルタ (B1') と同じ問題を重複処理
2. **欧州流動性の損失**: UTC14=CET15:00 (欧州午後), UTC17=CET18:00 (欧州夕方)。BTC/JPY に二方向流動性を提供する時間帯を静的に遮断するのは機会損失
3. **最良レジームの抑圧**: §3.1 trending_down_buy (+1.888bps, 最良) がこの時間帯で発生すれば、time_filter が利益機会を潰す
4. **B1' の包含性**: B1' は `regime=="ranging" AND vol_ratio < threshold AND side=="buy"` でフィルタ。時間帯に依存せず、UTC14/17 の損失ケースの大半を包含的に処理

**原則**: 条件ベースフィルタ (regime/vol) が時間ベースフィルタに優先する。時間フィルタは「他の全てのフィルタで対処不能」な場合の最後の手段とする。
