## 2. 各コンポーネントのコード実証とセカンドオピニオン

### 2.1 評価環境 (checkpoint_eval_env) の分離 (384#)
*   **実証**: `scripts/v460/lib/tasks/sac_train.py` を確認。
    ```python
    checkpoint_eval_env, _ = _create_training_env(train_df, cfg)
    checkpoint_metrics = _train_with_checkpoints(..., checkpoint_eval_env=checkpoint_eval_env)
    ```
    明示的に別インスタンスとして環境が生成され、SB3の内部状態（`_last_obs`等）が訓練環境と衝突するCRITICALバグは確実にコードレベルで修正・分離されています。
*   **セカンドオピニオン**: この修正は完璧です。これにより学習プロセスへのバイアス混入（Ghost State）が防がれました。

### 2.2 設定監査と手数料（Fee）の修正 (385#, 386#)
*   **実証**: `g2_sac_train.yaml` を確認。
    ```yaml
    transaction_cost: 0.0            # Coincheck Maker 0%
    reward_scaling: 1.0
    continuous_to_discrete_threshold: 0.10
    ```
    CoincheckのMaker手数料（0%）の仕様が完全に無視され片道10bps引かれていた設定が修正されました。また `reward_scaling` が PPOベースの暗黙値 6.0 から 1.0 に明示的に固定されました。
*   **セカンドオピニオン**: 手数料の誤適用はROIを人為的にマイナスに押し下げる最大の元凶でした。強化学習エージェントが「トレードしないのが最善」と学習する根因がこれで取り除かれています。方針として文句なしの「是」です。

### 2.3 報酬関数（Penalty過剰）のチューニング (387#)
*   **実証**: `ztb/trading/environment/components/calculators/reward_calculator.py`
    旧実装においては、PnL報酬（利益）に対し、外側で加算される `balance_penalty` や内部の `position_penalty`・`hold_penalty` が過大に設計されており、エージェントが利益追求ではなく非合理な「ペナルティ回避行動（Reward Hacking）」に走る構造でした。
*   **セカンドオピニオン**: ペナルティ比重の適正化は前進ですが、389#で指摘されている通り、**これでモデルが完成したと錯覚しないこと**が重要です。ペナルティを減らしたことでG2（訓練ゲート）は通貨（PASS）しやすくなりますが、それは単に「制約が緩くなって正のROIが出しやすくなった」だけであり、ライブ相場のエッジを捉えた証拠ではありません。

### 2.4 G3 (Profit/PnL) 評価への移行計画 (388#, 389#)
*   **現状分析**: G2のOOS成績をもってG3の要件（Profit Factor, ドローダウンなど）に突入しようと計画しています。
*   **セカンドオピニオン**: 389#が指摘する「実装の重複（二重化）を防ぐ」という視点は至言です。
    今まで（Ph1〜2）、我々は評価指標や計算ロジック（PnLやFeeの計算等）を至る所にコピペし、結果的に「Ghost Metric（幻想の評価）」を生み出してきました。
    G3の指標計測は**既存の `order_monitor.py` や `fill_test` の枠組み/集計スクリプトをベースに再利用し、絶対に独自の集計コードを新設しないこと**を強く推奨します。
