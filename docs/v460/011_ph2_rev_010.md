## §0 総評

010の中核主張「G1 FAILのままRLや収益化へ進むべきでない」は、000# §3.2 と整合し妥当。  
一方で、実装・運用に落とす段階で以下の矛盾があり、ここが迷走の主因になっている。

1. 収益モデルの断定が強すぎ、検証可能な仮説に分解されていない  
2. G1.1 の位置づけ変更が 000# の Gate 定義と未同期  
3. 「観測だけで0円運用」と「AS/fill品質の実測」が同時に成立しない  
4. 既存実装を使わず新規パスを提案しており、v459 の反省（重複実装）を再発

---

## §1 事実ベースの点検

### 1.1 010の妥当な部分

- `G1 FAIL -> 特徴量再設計優先` は正しい（000# §3.2, 006# 結論と一致）。
- `スケーリング先行は危険` の指摘は妥当（010 §5.3）。
- `G1.1は執行品質・AS測定として価値がある` は妥当（010 §6.2, 009# §1.2）。

### 1.2 現時点ログで確認できること

- `results/v460/fill_test/fill_records_20260213.jsonl` は **3件のみ**。  
  - fill rate: 2/3 = 66.7%  
  - cancel ratio: 33.3%  
  - queue wait median: 約5.0秒  
  - post_fill_30s_pnl 平均: -0.331 bps  
  - adverse selection ratio: 100%
- ただし n=3 のため、統計判断には全く不足。

## §3 過去資料との照合

### 3.1 v459の失敗学習との一致点

- `docs/v459/116_phase_e0_diagnostic_report.md` は「threshold調整は取引頻度を下げるだけで予測力を作らない」と結論。  
  010の「周辺最適化より信号源再設計を優先」は、この教訓と整合。

### 3.2 v459の失敗学習との不一致点

- `docs/v459/119_v460_launch_integrated_policy.md` は「重複実装を避け、既存基盤を使い切る」方針。  
  010のR1新規 collector 提案はこの方針に反する。

### 3.3 v460内レビュー資産の未活用

  010はこの整理を一部取り込みつつ、G1.1再定義で再びガバナンスを崩している。

## §4 方針修正（提案）

### 4.1 まず決めるべき原則

1. **Gateを変えるなら先に000#改定**（後追い解釈は禁止）  
2. **実装追加前に既存資産を使う**（`market_data_collector.py`, `run_fill_test.py`, `fill_quality.py` を優先）  
3. **主張は断定ではなく検証可能仮説へ分解**

### 4.2 実行トラックを3本に分離

- `Track A: Edge検証`  
  - 目的: direction/magnitude の情報量再確認  
  - 出口条件: G1再評価で PASS/FAIL を明確化
- `Track B: 執行品質計測`  
  - 目的: fill/AS/queue の実測  
  - 条件: 最小サイズの実注文を許容（観測のみでは不可）
- `Track C: 収益モデル更新`  
  - 目的: A/Bの実測値で 010 の仮定を置換（AS, fill率,回転率）

### 4.3 直近2週間の現実的プラン

1. Day 1: 000#改定要否を明記（G1.1期間を3日にするなら正式に枝番化）  
2. Day 1-3: 既存 `run_fill_test.py` で n>=200 サイクル収集（0.001 BTC、安全制約維持）  
3. Day 4: `fill_quality.py` で暫定メトリクス化、AS推定レンジを更新  
4. Day 5-8: 実板特徴量を既存パイプラインに追加し G1再実行  
5. Day 9-10: 継続/中止判定（G1 PASSなしなら v460縮退または v461移行）

## §5 範囲外だが効く改善提案

1. **非方向型 maker 戦略の並走検証**  
   - quote skew + inventory control のみでASを抑える設計（direction edge 依存を下げる）。
2. **取引所分散テスト**  
   - Coincheck単独でなく Bitflyer でも同一計測を行い、AS/fillの市場依存性を切り分ける。
3. **イベント駆動ターゲット化**  
   - 固定horizon（h1/h5/h15）だけでなく、イベントバーや出来高同期バーでも情報量検証。
4. **損益モデルをモンテカルロ化**  
   - 単一点の spread/AS ではなく、実測分布（時間帯・レジーム別）で月次PnLレンジを出す。
5. **継続中止ルールの先出し**  
   - 「この条件で停止」を先に決める（例: n>=500でAS>spread/2が継続なら停止）。

## §6 最終判定

010は「問題を正しく危機認識した文書」としては有効。  
ただし、そのまま実行計画に使うと以下が起きる。

- Gate運用が曖昧化する
- 実装重複が再発する
- 観測データだけ集まり、意思決定指標が増えない

したがって、次の一手は「追加実装」ではなく **方針同期（000#更新）と既存実装での短期実測** が先。
