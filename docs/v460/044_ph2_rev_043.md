## 2. 043への評価

### 妥当だった点

1. Bug 7（多重プロセス）を CRITICAL として認識した点  
2. PnL がマイナス継続であることを隠さず記録した点  
3. 方策Aの相反条件（fill と AS）を問題化した点  

### 不足していた点

1. Gate 閾値の公式/暫定の境界が曖昧  
2. 汚染データの除外基準が未定義  
3. 「高収益化」へ直結する実験デザイン（因果比較）の記述が弱い  

---

## 3. 収益化のための即時方針 (v459教訓・v451/v454反映)

### 3.1 やるべきこと

1. **データ統制を先に完了**  
   `valid_run` 条件: `git_sha!=None`, `run_id!=None`, 同一 lock epoch, schema coverage 100%。
2. **評価軸を PnL 中心に統一**  
   fill/AS は制約、最適化対象は `post_fill_30s_pnl` と実損 JPY。
3. **side 非対称最適化**  
   現状は sell 側が弱い。`offset_buy != offset_sell` を第一候補にする。
4. **レジームは入力より先に“運用タグ”として使う**  
   v454 の逆説（確信の大きさが負ける）を踏まえ、まず分解分析に徹する。  

### 3.2 やってはいけないこと

1. Gate 閾値を緩めて PASS を作ること  
2. 汚染データ込みで adaptation を回すこと  
3. ph2段階で行動空間を拡張すること（v451 の簡素化教訓に反する）

## 4. 実行計画（短期）

### 48時間以内 (P0)

1. `run_fill_test.py` に単一起動ロック実装（lockfile + file lock + stale回収）  
2. `results/v460/fill_test` を run 単位ディレクトリ化（追記混線を禁止）  
3. 再集計スクリプトを追加し、`clean.csv` と `quarantine.csv` を分離  
4. Gate判定は clean データのみで再算出  

### 7日以内 (P1)

1. side別 offset A/B（buy/sell 非対称）  
2. time_filter ON/OFF 比較（同時間帯の対照を作る）  
3. deadzone 0.5/1.0/2.0 の感度分析（coverage付き）  
4. 判定は p-mean + Holm で統一  

### 14日以内 (P2)

1. regime×side×spread_bin×hour の4次元評価テーブル固定化  
2. expected edge が負のセルは取引停止（ルールベース）  
3. Champion/Challenger で勝者設定のみ本線反映

## 6. 最終判断

043は「問題を正しく掴んだ報告」として有用。  
ただし現段階の最優先は **収益改善より先に、判定の信頼性（データ統制 + Gate整合）を回復すること**。  
この順序を守れば、ph2のままでも高収益に直結する改善（side非対称、時間帯・レジーム条件、toxic flow回避）へ進める。
