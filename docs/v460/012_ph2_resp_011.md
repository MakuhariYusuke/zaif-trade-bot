## §1 011 指摘の個別検証

### 指摘 #1 (HIGH): 「IC≈0 なら絶対に儲からない」は断定が過剰

**011 の主張**: 方向予測戦略としては妥当だが、spread・queue・inventory による非方向型マーケットメイキング (MM) 収益の余地が理論上残る。

**検証結果: 部分的に妥当 — ただし過大評価のリスクあり**

- **理論的には正しい**: 古典的 MM (Avellaneda-Stoikov 型) は方向予測なしでも spread capture + inventory control で期待正の PnL を得られる。
- **しかし v460 の設計前提と矛盾する**: 000# §0 は「Microstructure Edge」として「マイクロストラクチャ特徴量の導入と maker-only 執行戦略」を掲げている。§4 の技術概要も「情報量検証 → XGBoost Walk-Forward → G1-info」という**方向予測前提のパイプライン**を定義しており、非方向型 MM は v460 のスコープ外。
- **実務的な障壁**: Coincheck は WebSocket ストリーミングを提供しておらず、REST ポーリングのみ（poll_interval_sec = 5.0）。MM は連続的な双方向クオートが要件であり、5 秒間隔のポーリングでは latency が致命的。かつ、板の top-10 bid 深度は 0.166 BTC と極めて薄く、自己の注文が板の構造を変えるリスクが高い。
- **Gate 体系への影響**: 非方向型 MM を本気で検討するなら、000# の Gate 定義（特に G1-info が「方向予測能力」を検証する設計）を根本から改訂する必要がある。011 §5.1 で確かに提案されているが、「余地がある」を超えた具体的フィージビリティ評価がない。

**判定**: 理論的余地の指摘としては妥当だが、v460 の設計・インフラ制約下では**直近の現実的選択肢ではない**。将来的に v461 以降で検討する価値はあるが、010 の文脈（v460 の現状評価）で断定が「過剰」とまでは言えない。

**アクション**: 010 §9 の費用見積を修正し、Track を以下に分離:
- **観測トラック** (0 JPY): Coincheck API で orderbook/trade を polling → raw data 蓄積 → 特徴量候補の探索
- **実測トラック** (~1,000-5,000 JPY): `run_fill_test.py` で最小ロット実注文 → fill/AS 計測

## §2 011 が見落とした指摘

### 追加指摘 A (HIGH): 010 の PnL モデルに maker-maker 両約定確率が未考慮

010 §3 の PnL 式:

$$E[\text{PnL}] = (\alpha + s - 2 \cdot \text{AS}) \times V$$

この式は**エントリーとイグジットの両方が maker で約定する前提**で spread s = 1.08 bps を全額獲得しているが、現実には:

1. エントリーは best bid/ask に置くが、イグジット注文は保有期間後に価格が動いた位置で出す → **イグジットの約定位置は best bid/ask と一致しない**
2. イグジットが maker で約定しない場合（タイムアウト等）、taker での強制決済が発生 → taker 手数料 0.1% = **10 bps の追加コスト**
3. fill rate が 90% なら、10% のイグジットは taker → 期待コスト: 0.1 × 10 bps = 1.0 bps/trade が加算

修正後の PnL 式:

$$E[\text{PnL}] = (\alpha + f_{mm} \cdot s - 2 \cdot \text{AS} - (1-f_{mm}) \cdot c_{\text{taker}}) \times V$$

- $f_{mm}$: both-legs-maker 確率
- $c_{\text{taker}}$: taker 手数料 (10 bps)

**影響**: AS = 1.0 bps, $f_{mm}$ = 0.81 (fill rate 90% の両レグ = 0.9²) とすると:
- spread 獲得: 0.81 × 1.08 = 0.87 bps（1.08 → 0.87 に低下）
- taker コスト: 0.19 × 10 = 1.9 bps
- $E[\text{PnL}]$ = (α + 0.87 - 2.0 - 1.9) × V = **(α - 3.03) × V**

→ IC ≈ 0 ではなく**あらゆる IC で損失**になる。ブレークイーブン IC は 0.13 に跳ね上がる。010 のシナリオ B (IC=0.05) すら大幅赤字。

この見落としは 010 の結論（「儲からない」）を強化する方向だが、**定量的な根拠が変わる**ため記載すべきだった。

011 §1.2 は n=3 のデータを引用し「統計判断には全く不足」と簡潔に片付けているが、データ内容を見ると以下の所見がある:

|-------|------|--------|-----------|---------------------|-----------------|

## §5 判断のための考察（000#改訂 vs 先行着手）

### §5.1 二択の比較

| 選択肢 | 利点 | リスク | 判定 |
|---|---|---|---|
| A: 000# を先に全面改訂 | Gate ガバナンスが明確、後戻りが少ない | 着手が遅れ、実測データが増えない | 単独では遅い |
| B: 改訂せず着手優先 | 速度が出る、実測で学べる | 後から「ルール違反」扱いになりやすい | 単独では危険 |
| C: **最小改訂 + 並行着手** | ガバナンスと速度を両立 | 事前に境界を明文化する必要 | **推奨** |

### §5.2 境界線（どこまで先に着手してよいか）

**000#改訂が先な作業**:

1. Gate 判定条件そのものを変える（例: G1.1 の 7日 -> 3日）
2. PASS/FAIL 閾値を変更する
3. Gate の正式判定として成果を主張する

**改訂前でも着手可能な作業**:

1. 観測データ収集（orderbook/trades の raw 蓄積）
2. 既存実装の安定化・バグ修正
3. 収集データの探索分析・特徴量候補整理
4. 小額の予備実測（ただし「正式G1.1判定」とは分離して記録）

### §5.3 実務的な推奨手順（48時間）

1. **Day 0 (半日)**: 000# の最小改訂案だけ先に確定  
   - 変更点は `§3.3 G1.1-exec` の測定期間定義のみ（必要なら枝番で暫定運用を明記）
2. **Day 0-2**: 既存 `run_fill_test.py` と `MarketDataCollector` で収集を継続  
   - ここでは「判定」ではなく「計測」に限定
3. **Day 2**: n と品質を確認して正式 Gate 判定フェーズへ移行するか判断  
   - 目安: サンプル数・時間帯カバレッジが閾値に達していること

### §5.4 最終提言

「000#を改訂してから動くか、先に動くか」の二者択一ではなく、  
**最小改訂を先に固定し、非判定タスクは即時並行実行**が最も損失が小さい。

- ガバナンス破綻を防げる
- データ収集の機会損失を避けられる
- 後からの文書差し戻しを最小化できる
