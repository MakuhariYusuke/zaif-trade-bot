## §2 指摘別評価

### §2.1 Finding #1: G1 判定実装の二重基準 — **受理 (CRITICAL)**

| 項目 | 内容 |
|------|------|
| 分類 | CRITICAL |
| 評価 | **完全に妥当** |
| 対応 | 即時修正 |

**検証結果**:

2 つの実行経路で判定ロジックが異なることを確認。

| 実行経路 | 判定ロジック | 追加チェック |
|----------|-------------|-------------|
| `run_experiment.py:_evaluate_gate()` (L131) | `g1_judgment()` のみ | なし |
| `run_gate_check.py:run_g1_judgment()` (L125) | `g1_judgment()` + extra threshold checks | min_ic, min_accuracy, min_significant_folds を **全 target AND** |

001# §5.3 の仕様式:

```
G1_PASS = ∃ target: (holm_pass(target) ∧ pmean_pass(target) ∧ |d(target)| > 0.33)
```

`run_experiment.py` の実装は `g1_judgment()` のみで `any()` ロジック — **仕様準拠**。  
`run_gate_check.py` は追加で `all()` による全 target チェックを AND しており — **仕様違反**。

**根本原因**: 003# review #6 で `run_gate_check.py` に追加閾値チェックを入れた際、000# §3.2 の「1 組合せでも PASS」条件を見落とした。

### §2.2 Finding #2: 全ターゲット閾値の `all()` 要求 — **受理 (HIGH)**

| 項目 | 内容 |
|------|------|
| 分類 | HIGH |
| 評価 | **完全に妥当** |
| 対応 | Finding #1 と一体修正 |

**検証結果**:

```python
# run_gate_check.py L153-155
extra_all_pass = all(
    c["ic_pass"] and c["accuracy_pass"] and c["sig_folds_pass"]
    for c in extra_checks.values()
) if extra_checks else False

final_pass = judgment["g1_pass"] and extra_all_pass
```

000# §3.2 より:

> **Multi-target**: …1 組合せでも PASS すれば G1 通過。

仕様は `∃ target` (any) であり、`∀ target` (all) ではない。  
`all()` では 9 target すべてが IC/Accuracy/有意 fold をクリアしないと通過しない — これは仕様の **逆** の実装。

**影響度**: 今回の G1 結果自体には影響しない（`g1_judgment()` が cliff_d 不足で既に FAIL のため `final_pass` にかかわらず FAIL）。  
ただし将来の再実験で偽 FAIL を生む直接的なリスクがある。

### §2.3 Finding #3: `aggregate_to_1min()` 引数なし呼び出し — **受理 (HIGH)**

| 項目 | 内容 |
|------|------|
| 分類 | HIGH |
| 評価 | **完全に妥当** |
| 対応 | 即時修正 |

**検証結果**:

`aggregate_to_1min` は `@staticmethod` で 3 引数が必須:

```python
# ztb/data/market_data_collector.py L175-177
@staticmethod
def aggregate_to_1min(
    ob_path: Path, tr_path: Path, output_path: Path
) -> pd.DataFrame:
```

呼び出し側 (L308, L320):

```python
self.aggregate_to_1min()  # 引数なし → TypeError
```

`self.` 経由で呼んでいるが `@staticmethod` なので `self` は渡されず、3 引数すべてが欠落。  
結果: `auto_aggregate=True` 時は **必ず** `TypeError` が発生し、`except Exception as e` で `"Auto-aggregate failed: {e}"` の warning ログを出して握りつぶされる。

**実害**: G1 実験は `auto_aggregate` を使わないため今回は影響なし。  
G1.1 (実板データ収集) では致命的。

### §2.4 Finding #4: `fold_results` 生配列による JSON 肥大化 — **受理 (MEDIUM)**

| 項目 | 内容 |
|------|------|
| 分類 | MEDIUM |
| 評価 | **妥当** |
| 対応 | 段階的改善 |

**検証結果**:

```python
# scripts/v460/lib/tasks/feature_info.py L118
"fold_results": fold_results
```

`fold_results` 構造: `{target_name: [(model_scores, baseline_scores), ...]}` — 各 fold で 48,677 floats × 2 配列 × 5 folds × 9 targets ≈ **4.38M float 値**。

JSON シリアライズ時: 1 float ≈ 30 bytes (decimal + comma + space) → 約 **131MB** → 圧縮前 142MB は整合。

**影響**: I/O 遅延、ディスク圧迫。ただし Gate 判定には `fold_results` の生データが必要（`g1_judgment` が fold 別統計検定を行うため）。

| Step | 提案内容 | 評価 | 対応 |
|------|----------|------|------|
| Step 1 | Gate 判定の単一化 | ✅ 必須 | 本 007# で即時実装 |

| Step 5 | 成果物スリム化 | ✅ 妥当 | 本 007# で debug モードフラグ追加 |

### Step 2 保留の理由

006# は「volatility を G1 判定から分離せよ」と提案するが、以下の点で慎重を要する:

1. **仕様変更の波及**: 000# §3.2 は 9 target を 1 family として Holm 補正する設計。volatility 除外は family サイズ変更を伴い、補正の統計的妥当性に影響する。
2. **情報の喪失**: volatility 予測能力は RL フェーズの報酬設計 (position sizing) に直接活用可能。補助指標として保持する価値がある。
3. **タイミング**: 現在 G1 は cliff_d 不足で全 target FAIL。volatility 分離は alpha が存在する前提での最適化であり、現時点では premature optimization。

→ G1 再実験で direction 系に alpha 証拠が確認された段階で、target 再編を仕様変更提案として別途議論する。

## §5 修正の詳細設計

### F1/F2: Gate 判定統一

**方針**: `run_gate_check.py` の追加閾値チェックを target 単位 `any()` に変更し、`g1_judgment` 結果との AND を正しく構成する。

```python
# Before (仕様違反):
extra_all_pass = all(c["ic_pass"] and c["accuracy_pass"] and c["sig_folds_pass"]
                     for c in extra_checks.values())
final_pass = judgment["g1_pass"] and extra_all_pass

# After (仕様準拠):
extra_any_pass = any(c["ic_pass"] and c["accuracy_pass"] and c["sig_folds_pass"]
                     for c in extra_checks.values())
final_pass = judgment["g1_pass"] and extra_any_pass
```

さらに、`g1_judgment` が PASS した target のみを extra check 対象とする改善も行う（PASS 候補以外の target で閾値チェックする意味がないため）。

### F3: `aggregate_to_1min()` 引数修正

**方針**: `run_continuous()` 内で `self` のパス属性から `ob_path`, `tr_path`, `output_path` を構築して渡す。

### F4: 成果物スリム化

**方針**: `fold_results` のデフォルト保存を統計量のみ (p 値, 効果量, サンプル数) にし、`--debug` フラグ時のみ生配列を保存する。Gate 判定は保存前に実行するため、`g1_judgment()` への入力には影響しない。

## §6 006# で見落とされた追加指摘

006# レビューが対象としたスコープ外で、さらに 4 件の問題を発見した。  
特に F5 は 007# F4 修正自体が新たに導入した自己矛盾バグであり、即時修正が必要。

### §6.1 Finding F5: 007# F4 が `run_gate_check.py` 再判定を破壊 — **CRITICAL (自己矛盾)**

| 項目 | 内容 |
|------|------|
| 分類 | CRITICAL |
| 原因 | 007# F4 自体のバグ |
| 対応 | 即時修正 |

**問題**: 007# F4 で `run_experiment.py` が `fold_results` を stats-only (`fold_results_saved`) に差し替えて JSON 保存するようにした。しかし `run_gate_check.py` はこの保存済み JSON を読み込んで `g1_judgment()` を再実行する。`g1_judgment()` は `dict[str, list[tuple[list[float], list[float]]]]` を期待するが、stats-only JSON では `dict[str, list[dict]]` が入っており、fold ループで展開不能となりクラッシュする。

```python
# g1_judgment() 内部:
for model_scores, baseline_scores in folds:  # ← dict は unpack 不可 → ValueError
```

**影響**: `run_gate_check.py --gate G1` が 007# 以降に保存された全ての結果 JSON で動作不能になる。

**修正方針**: `run_experiment.py` で Gate 判定結果を JSON にキャッシュし、`run_gate_check.py` はキャッシュがあればそれを使用する。

### §6.2 Finding F6: `_evaluate_gate()` が extra threshold を未チェック — **HIGH (不完全修正)**

| 項目 | 内容 |
|------|------|
| 分類 | HIGH |
| 原因 | 006# Finding #1 の修正が不完全 |
| 対応 | 即時修正 |

**問題**: 007# F1/F2 は `run_gate_check.py` の `all()` → `any()` を修正したが、`run_experiment.py._evaluate_gate()` は依然として `g1_judgment()` のみで判定している。  
Gate 判定の二重基準は **依然として残存** している:

| 経路 | g1_judgment | IC/Accuracy/Sig folds |
|------|:-----------:|:---------------------:|
| `run_experiment.py._evaluate_gate()` | ✅ | ❌ |
| `run_gate_check.py.run_g1_judgment()` | ✅ | ✅ (any) |

**影響**: `run_experiment.py` 経由の G1 判定が `run_gate_check.py` よりも **緩い**。

**修正方針**: `_evaluate_gate()` にも IC/accuracy/significant_folds の `any()` チェックを追加し、判定ロジックを統一する。

### §6.3 Finding F7: `_deep_merge()` が `_task` を消失させる — **MEDIUM**

| 項目 | 内容 |
|------|------|
| 分類 | MEDIUM |
| 原因 | `config_loader.py` の meta key 処理 |
| 対応 | 即時修正 |

**問題**: `_deep_merge()` は `_` prefix のキーをすべてスキップする。`load_config()` は `_base`, `_gate`, `_experiment` を明示的に復元するが、`_task` は復元されない。

実験 YAML には `_task: feature_info` が定義されているが、マージ後の dict に反映されない。  
`run_experiment.py` は `cfg.get("_task", "feature_info")` でデフォルト値を使うため、現状は動作する。  
しかし将来 `_task: sac_train` など別タスクが追加された場合、常に `feature_info` が実行される **潜在バグ**。

### §6.4 Finding F8: trade dedup の文字列比較 — **LOW**

| 項目 | 内容 |
|------|------|
| 分類 | LOW |
| 原因 | `market_data_collector.py` |
| 対応 | G1.1 実装時 |

**問題**: `_append_raw_trades()` で `trade_id = f"{t.timestamp}:{t.price}:..."` を文字列として `<=` 比較している。形式変更時に辞書順 ≠ 時系列順となるリスクがある。現時点では低リスク。
