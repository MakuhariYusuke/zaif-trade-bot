（※`avg_final_stage`: `maker_price.py` が出力したCeiling後のOffset。`avg_eff_offset`: 最終的に相場に投げられた実効Offset）

### 🔍 考察とセルフレビュー：405# は「犯人」か「起爆剤」か
*   **Codex(416#)の正しさ**: 3/11〜3/12の段階で、`avg_final_stage` は設定通り `0.30` に見事にクランプされています。しかし、実際に適用された `max_eff_offset` は `1.305` や `0.942` と、0.30の天井を完全にブチ抜いています。これは `fill_cycle_executor.py` が多数の乗数（VG、Toxicity等）を **Ceilingの適用後に野放図に掛け合わせている** ためです。
*   **415#の主張の「拾い上げるべき点」**: 415#はこれを「405#が0.50に緩和したから悪化した」と結論づけました。これは原因の特定としては誤りですが、現象としては辻褄が合います。なぜなら、掛け算のベースとなる `final_stage` の値が 0.3 から 0.5 に底上げされたことで、**「ベース(0.5) × 後段の乗数」という最悪のコンボ**が発動し、全体のアベレージを `0.524` という「絶対に刺さらない（刺さる時は大暴落の時だけ）破滅的な乖離」へと追いやった「起爆剤」になったからです。

**【結論】**
Ceilingを0.35にするか0.40にするかの議論は**現在無意味**です。まずはExecutorの最後段で強制的に `max_offset_ratio` を適用する「The Final Clamp」を実装しなければ、全ての設定値が砂上の楼閣となります。

## 2. `sell_dynamic_kill` はノイズではなく「死の螺旋」の証明

415#では、SDK（`sell_dynamic_kill`）が頻発した現象を「残高制限下によるノイズであり、有効サイクルを減らしただけ」と結論づけました。しかし、これは市場の叫びをミュートする危険な解釈です。

Codex（416#）が指摘した `[balance] buy insufficient → switch to sell → SDK blocked` のデッドロックは、以下のような**「インベントリの極端な非対称性（片肺飛行）」**を表しています。

1. **なぜ買う残高（JPY）がないのか？** → 買い注文ばかりが約定し、BotがBTCを抱え込んでいるから。
2. **なぜ売る残高（BTC）がないのか？** → 上記1と一見矛盾しますが、これは「Sellが遠すぎる（Offset天井崩壊）」ために全く約定せず、仕方なく「Sellの待機制限（あるいは評価基準）」に引っかかり、建玉が解消されないまま滞留しているか、逆に損失を恐れてSellそのものを諦めきっている状態（あるいは小ロットで細かく削られている）のいずれかを示唆しています。
3. **死の螺旋**: 「買うお金がないから売りに行けと言う。しかし売るためのBTC（閾値2mBTC）もないからSDKで殺す」。このRoute-to-killデッドロックにより、サイクル全体が麻痺しています。

**【結論】**
SDKはノイズではなく「ボットが相場の波に乗れず、手足をもがれた状態」になることの証明です。根本原因は前述の「偏ったOffset（刺さらない売り）」にあり、それによってインベントリ・サイクルが自壊しています。

## 3. 実装・運用へ向けた本質的アクション（Actionable Plan）

多角的な視点とデータ再集計を踏まえ、以下の順序で改修・分析を実行することを提案します。

### Action 1. 【最優先/P0】The Final Clamp の導入
*   `scripts/v460/lib/pre_order_adjustments.py` または `fill_cycle_executor.py` の**発注直前（全ての影響乗数を掛け終わった後）**に、全体構造を保護する最終的なCeilingチェック処理を挿入してください。
*   これにより、`effective_offset_used` はいかなる場合も `max_offset_ratio` （YAMLで指定された上限）を絶対に超えないようになります。

### Action 2. 【P1】Orchestrator デッドロックの脱出経路構築
*   Codexの指摘通り、`orchestrator_balance.py` において「opposite sideへ切り替える際、そのsideもすでにKillされている（残高がない等）」場合は、即座にSDKによる連続エラー（ログの埋め尽くし）を起こすのではなく、明示的に `Idle / Backoff` を選択して数秒待機する分岐を追加してください。

### Action 3. 【P1】SkipGate の「Pnl Mode」閾値の再調査
*   415#の指摘した「SellのSkip率が2%しかない」という現象自体は事実です。
*   すでに実装済みのSide別Adaptive Threshold（`mode: pnl`）において、なぜSell側のScore分布が閾値を超えられていないか（モデルがSellリスクを過小評価しているThe Confident-Wrong Paradoxの再来か）を、`skip_gate_score` の分布ヒストグラムから分析する必要があります。

### Action 4. 【P2】SHAごとの再評価（Mixed-SHAの解体）
*   時間帯分析や405#の影響評価は、日次ではなく `git_sha` 単位で行う必要があります。日次の集計はトレンドを掴むためには役立ちますが、コードの責任分解点（Attribution）を特定する際には誤った因果関係を生むリスク（415#の罠）があります。

### セルフレビュー（自己批判）
「The Final Clampを入れれば全て直る」と過信してはいけません。相場変動（Volatility Guard等）によるBoostは、本来「危険だから遠ざける」ための正当な防衛メカニズムです。それを強引に1つの上限（例: 0.3）でクランプしてしまうと、「本来なら0.8まで逃げるべき暴落相場なのに、0.3で待機してしまい巨大な逆選択（AS）を喰らう」という逆効果を引き起こすリスクがあります。
したがって、Final Clampの導入に合わせて、**「上限を超えるような危険なBoostが計算された場合、価格を遠ざけるのではなく、注文そのものを明確に『Skip（発注見送り）』するロジック（Hard Skipの確実な発動）」**をセットで設計することが、真の強靭化に繋がります。
