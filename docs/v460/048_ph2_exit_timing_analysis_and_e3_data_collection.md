## §1 概要

v460 fill test の約 385 件の取引履歴を包括的に分析し、**exit timing 最適化**の余地を定量的に評価した。分析の結果、現システムが構造的にマイナス期待値であること、その主要因が **adverse selection** と **win/loss 非対称性** にあることを特定。改善のデータ基盤として **E3: Multi-Timeframe PnL 計測** (30/60/120 秒) を実装し、次フェーズでの exit timing 最適化に必要なデータ収集を開始した。

### §1.1 本文書の目的

- 外部 AI コーディングエージェントに対してシステムの現状と課題を正確に伝達
- exit timing 最適化の具体的改善案を策定するための定量的根拠の提供
- ph3 実装に向けたロードマップの提示

## §2 システムアーキテクチャ

### §2.1 取引フロー

```
[サイクル開始]
  ↓
  preflight check (残高・安全停止)
  ↓
  time_filter 判定 → skip_utc_hours に該当 → sleep 120s → 次サイクル
  ↓
  orderbook 取得 → spread 計算
  ↓
  maker 注文発注 (buy/sell 交互)
    → spread_offset_ratio × spread だけ有利側にオフセット
  ↓
  ポーリング (5s 間隔, 最大 300s)
    → 約定: fill_price 記録
    → タイムアウト/エラー: cancel_reason 記録
  ↓
  [約定時] post-fill PnL 計測
    → 30s 後: mid_30s_after → post_fill_30s_pnl
    → 60s 後: mid_60s_after → post_fill_60s_pnl  ← E3 (新規)
    → 120s 後: mid_120s_after → post_fill_120s_pnl  ← E3 (新規)
  ↓
  FillRecord 保存 (JSONL)
  ↓
  cycle_interval_sec (120s) 待機
  ↓
  [次サイクル] side 反転 (buy → sell → buy → ...)
```

### §2.2 重要な構造的特徴

| 項目 | 現状 | 影響 |
|---|---|---|
| ポジション管理 | **なし** (各サイクル独立) | exit timing の概念が存在しない |
| side 決定 | **機械的交互** | 市場方向と無関係 |
| 注文価格 | `mid ± spread × offset_ratio` | AS 回避が主目的 |
| PnL 計測 | **観察のみ** (30s 後の mid で評価) | 実際の収益には反映されない |
| exit 戦略 | **存在しない** | 約定後は放置、次のサイクルの反対売買が "暗黙の"exit |

**重要**: 現在のシステムは「maker 注文の品質評価 (fill test)」が主目的であり、実際の P&L 最小化/最大化ロジックは未実装。post_fill_30s_pnl は「もし約定時点でポジションを取り、30 秒後に mid で手仕舞いした場合の仮想 PnL」を計測している。

### §2.3 設定パラメータ (configs/v460/fill_test.yaml)

| パラメータ | 値 | 説明 |
|---|---|---|
| `symbol` | btc_jpy | Coincheck BTC/JPY |
| `order_quantity` | 0.001 BTC | ~10,500 JPY |
| `cycle_interval_sec` | 120.0s | サイクル間休止 |

## §5 約定品質の深掘り

### §5.1 約定待ち時間 vs PnL

| 待ち時間 | 件数 | 平均 PnL | AS 率 |
|---|---|---|---|
| 速い (≤10s) | 122 | **−0.88 bps** | **46%** |
| 中間 (10-60s) | 110 | **−0.95 bps** | **45%** |
| 遅い (>60s) | 59 | **+0.96 bps** | **27%** |

**重要な発見**: **約定が速いほど PnL が悪い**。即座に約定する注文は「市場がすでに逆方向に動いた後に拾われている」ことを示唆。遅い約定 (>60s) は queue 内で待たされた結果、市場が落ち着いた状況で約定するため AS 率が低い。これは **maker 注文の逆選択の教科書的な現象**。

| 普通 (1500-3000) | 37 | −0.88 bps | 35% |
| 広い (≥3000 JPY) | 31 | −0.66 bps | 32% |

**所見**: スプレッドが狭い時（≈1.4 bps）ほど PnL が悪い。狭スプレッドは流動性が一時的に集中しているタイミングであり、方向性のある参加者が大量に注文を消化している場面を意味する。maker として置かれた注文がこの流れに巻き込まれる。

## §6 モメンタム・連続性分析

### §6.1 自己相関

| ラグ | 相関係数 |
|---|---|
| 1 | **−0.051** |
| 2 | +0.157 |
| 3 | −0.023 |
| 4 | −0.073 |
| 5 | −0.042 |

ラグ 1 の微弱な負の相関は「直前の取引が勝ちなら次は負ける傾向」を示唆するが、絶対値が小さすぎて統計的に有意ではない。**PnL 系列はほぼランダムウォーク**であり、過去の PnL に基づくポジションサイズ調整は効果が薄い。

ラグ 2 の +0.157 は微弱に「2 つ前の結果が繰り返される」傾向だが、同様に有意性は低い。

### §6.2 連勝/連敗ストリーク

| 種別 | 最大 | 平均 | 出現回数 |
|---|---|---|---|
| 連勝 | 6 | 1.9 | 71 |
| 連敗 | **7** | 2.1 | 72 |

連敗ストリークがやや長い。平均連敗 2.1 回は **ドローダウン管理** の観点で重要 — 安全設計 (`loss_cap_auto`) の閾値が適切か要確認。

### §6.3 大勝利後のモメンタム

先行分析で確認済み: **大勝利 (>5 bps) 後のモメンタム継続率はわずか 27.3%** (3/11)。「勝っている時にもっと粘る」戦略は統計的に正当化されない。これは BTC/JPY の maker 環境では「有利な方向に動いてもすぐに mean-revert する」ことを示す。

## §7 サイクルタイム予算分析

### §7.1 現状 (pre-E3)

| 項目 | 値 |
|---|---|
| サイクル間隔 (inter-cycle) 平均 | 209.0s (3.5min) |
| サイクル間隔中央値 | 164.9s (2.7min) |
| 約定サイクル所要時間 (旧) | 193.9s = wait(43.9s) + meas(30s) + interval(120s) |
| 未約定サイクル所要時間 | 120.5s = wait(0.5~) + interval(120s) |
| 推定サイクル数/日 | **446** |

### §7.2 E3 適用後

| 項目 | 値 |
|---|---|
| 約定サイクル所要時間 (E3) | 403.9s = wait(43.9s) + meas(120s) + interval(120s) |
| 推定サイクル数/日 | **214** |
| **削減率** | **−52.0%** |

E3 による 120 秒計測 (30+30+60) で fill 時のサイクル時間が約 2 倍に延長。これは **データ収集フェーズの一時的なコスト** であり、十分なデータ (n≥200 程度) が揃えば、計測時間の最適化または不要な multi-timeframe 計測の廃止が可能。

### §7.3 サイクルタイムの改善余地

E3 データが「60s/120s 計測に有意な情報価値がない」と示した場合、30s のみに戻して効率を回復可能。逆に「120s 後の方が PnL 予測精度が高い」場合は、post_fill_wait_sec を 120s に延長する代わりに cycle_interval_sec を短縮し、ネット throughput を維持する設計に移行可能。

## §8 仮想 TP/SL シミュレーション

### §8.1 目的

現在の 30s 後 PnL データを用いて「もし TP (Take Profit) / SL (Stop Loss) を設定していたら」のバックテストを実施。これは **exit timing 最適化の方向性** を探るためのシミュレーション。

### §8.2 結果

| TP | SL | 累計 PnL | 勝率 | 平均 PnL | 評価 |
|---|---|---|---|---|---|
| 1 | 1 | −13.4 | 47.4% | −0.046 | ← ほぼブレイクイーブン |
| 2 | 1 | **+64.2** | 47.4% | **+0.221** | ✅ |
| 3 | 1 | **+120.3** | 47.4% | **+0.413** | ✅✅ |
| **5** | **1** | **+199.8** | 47.4% | **+0.687** | ✅✅✅ **最良** |
| 5 | 2 | +110.5 | 47.4% | +0.380 | ✅ |
| 5 | 3 | +47.2 | 47.4% | +0.162 | ✅ |
| 3 | 3 | −32.3 | 47.4% | −0.111 | ❌ |
| 5 | 5 | −40.1 | 47.4% | −0.138 | ❌ |

### §8.3 解釈

**TP ≫ SL (非対称 TP/SL) が有効**。特に TP=5 bps / SL=1 bps の組み合わせで累計 +199.8 bps と、現状の −155.2 bps から **+355 bps の改善** が理論上可能。

**しかし重要な注意点**:
1. これは「30 秒後の PnL が TP/SL 範囲内なら 30 秒 PnL をそのまま使う」というビン化であり、**実際の exit タイミングでの価格は不明**
2. TP=5 で SL=1 は「1 bps 逆行したら即座に成行で損切り」を意味し、**slippage や約定遅延で実現困難**
3. maker 注文のみのシステムでは exit も maker にする必要があり、即時 exit は困難
4. 実際には PnL が SL に達する前に SL を発動する必要があるため、価格パスの高頻度監視が必要

### §8.4 実装上の示唆

非対称 TP/SL の知見は以下の形で活用可能:
- **方針**: テールリスク (大損失) を早期に遮断し、利益方向には粘る
- **実装案 A**: tick-level 価格監視 + 逆指値 (成行) での損切り
- **実装案 B**: 次サイクルの side を「現在ポジションの逆を取る (= 実質 exit)」として、不利な場合のみ cycle_interval を短縮
- **実装案 C**: AS 検知時のみ即座に反対注文を出すことで、損失を限定

## §9 根本課題の整理

### §9.1 問題の構造

```
[逆選択 (AS)]  ←───  maker 注文の本質的弱点
     │
     ├── 約定時点で mid に対して不利 (edge = −0.37 bps)
     │
     ├── 速い約定ほど PnL が悪い (AS 46% for ≤10s)
     │
     └── 情報劣位: maker は taker の行動を事前予測できない


[Win/Loss 非対称]  ←───  テール分布の問題
     │
     ├── 平均勝ち +3.02 vs 平均負け −3.79 (比率 0.797)
     │
     ├── 最大損失 −31.4 bps vs 最大利益 +25.8 bps
     │
     └── [−100, −10) の 18 件が −265 bps を生成 (全損失の 46%)


[勝率] ←───  確率の問題
     │
     ├── 47.4% (コイントスよりやや不利)
     │
     └── side 交互で市場方向を無視 → 勝率 50% は理論上限
```

### §9.2 改善の優先順位

| 優先度 | 課題 | 改善余地 | 難易度 |
|---|---|---|---|
| **P0** | テール損失の制御 | 18 件 × −14.7 bps/件 = −265 bps 削減 | 中 |
| **P1** | AS 時間帯の更なる回避 | UTC 13 追加で −30 bps 回避 | 低 |
| **P2** | 速い約定への対策 | 即約定 = AS のシグナルとして活用 | 中 |
| **P3** | side 方向性の改善 | 交互→市場方向連動で勝率 50%超へ | 高 |
| **P4** | スプレッド条件の選別 | 狭スプレッド回避で −2.79 bps → 0 | 低 |

## §11 外部レビュー向け — 改善提案

### §11.1 即座に実装可能な改善 (Low-hanging Fruit)

#### R1: テール損失カット (P0)

**シナリオ**: 10 bps 超の損失 (18 件, −265 bps) を 5 bps で損切りしていれば:
- 回避可能な損失: 265 − 18×5 = **−175 bps**
- 累計 PnL: −155.2 + 175 = **+19.8 bps** (黒字化)

**実装案**: post_fill_wait_sec の 30 秒間に 5 秒間隔で mid price を確認し、−5 bps 到達で即座に反対注文を出す。ただし maker 限定のため taker exit は不可。代わりに:
- 次サイクルの interval を 0 秒にして即座に反対注文 → 実質 exit
- または soft_loss_cap に類似した「個別取引 loss cap」として cycle_interval を動的短縮

#### R2: time_filter 拡張 (P1)

UTC 13 (JST 22) を `skip_utc_hours` に追加: −30.0 bps 回避。

```yaml
time_filter:
  skip_utc_hours: [8, 9, 13, 14, 16, 17, 18, 19]  # UTC 13 追加
```

ただし件数 28 は time_filter 導入前のデータを含む可能性があるため、E3 新データで再検証が必要。

#### R3: 即約定フィルター (P2)

`queue_wait_sec ≤ 5s` の約定は AS シグナルと見なし、spread_offset_ratio を一時的に増加:

```python
if queue_wait_sec <= 5.0:
    # 次サイクルの offset を 2 倍に
    self.config.spread_offset_ratio = min(
        self.config.spread_offset_ratio * 2,
        self.config.adaptation.max_offset_ratio
    )
```

### §11.2 中期的改善 (E3 データ依存)

#### R4: 最適 Exit Window の決定

E3 の 30/60/120s データが揃えば (n≥200)、以下の分析が可能:

```python
# post_fill_Xs_pnl の分散安定性分析
# → "X 秒後に情報が飽和するか" を判断
for window in [30, 60, 120]:
    pnl = records[f"post_fill_{window}s_pnl"]
    incremental_info = mutual_information(pnl_30s, pnl_Xs)
    print(f"{window}s: incremental information value = {incremental_info}")
```

#### R5: 方向性予測モデル (P3)

side の交互ルールを廃止し、以下のシグナルで方向を決定:
- 直近の orderbook imbalance
- 直近 N 秒の mid price trend
- レジーム分類 (trending → trend follow, ranging → mean revert)

これは大幅なアーキテクチャ変更を伴うため、E3 データ分析後に着手。

### §11.3 長期的改善

#### R6: マイクロストラクチャを活用した Exit

tick-level の価格データ (WebSocket) を用いたリアルタイム exit:
- mid price の N-tick 移動平均クロス
- Volume-weighted price の逆行検知
- 約定後の orderbook 変化を monitoring

これは fill test フレームワークの外側の実装となり、live trading  エンジンの再設計が必要。

### §13.1 定量サマリ

| 指標 | 値 | 目標 |
|---|---|---|

### §13.2 最重要知見

1. **テール制御が最優先**: 全損失の 46% はわずか 6.2% の取引が生成。テール損失を 5 bps で蓋すれば理論上黒字化。
2. **AS は速度に依存**: 即約定 (≤10s) の AS 率 46% vs 遅延約定 (>60s) の AS 率 27%。これは逆選択の発生機序を示唆。
3. **非対称 TP/SL が有効**: TP=5/SL=1 で +200 bps (シミュレーション)。利益方向に粘り、損失方向は早期遮断。
4. **時間帯の選別が重要**: UTC 20-22 (JST 05-07) は正 PnL、UTC 16-19 (JST 01-04) は AS 60-70%。
5. **E3 データが鍵**: 60s/120s PnL データにより、exit timing の最適化根拠を定量的に獲得可能。
