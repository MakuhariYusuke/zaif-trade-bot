## §1. 時間帯制限（sell_hour等）の本質と多角的な視座

546# にて「sell_hourという時間帯ルールはYAMLで動的にしているからハードコードではない」と主張されました。しかしこれは、**「氷（固定観念）を別の冷蔵庫（YAML）に移しただけで、氷であることには変わりない」**という対処療法の域を出ないものです。

なぜ時間で制限をかけるべきではないのか、多角的な視点からその本質を紐解きます。

### 1.1 現象的・統計的視点（結果の観察）
過去のバックテストや運用で「12時台、15時台に損失が偏る」という現象が観察されました。これは事実です。ランチタイムやロンドン・フィキシングなど、機関投資家や特有のフローが市場に入る時間帯であるため、この時間に蓋をすれば「とりあえずの止血」にはなります。これが対処療法の正体です。

### 1.2 微視的構造（Market Microstructure）の視点（原因の特定）
時間が損失を作っているわけではありません。**その時間に発生する「流動性の枯伏（板の薄さ）」と「一方向への強い注文流（Toxic Flow / 逆選択）」が直接的な原因**です。
もし我々が543-545#で実装した `OFI-Lite`（注文総量の偏り）や `AS δ*`（逆選択コストの指標）が正常に機能するならば、12時だろうが15時だろうが、**指標が危険を察知して自動的にスプレッドを広げるか、取引を見送る（Boost上昇）はず**です。逆に言えば、OFIやδ*が安全視しているのに「15時だから」という理由だけで取引をストップするのは、明白な機会損失（過学習）です。

### 1.3 哲学的視点（風水渙・第三爻変）
易占から得た「渙（溶かす・散らす）」の真意は、**事象（過去のトラウマ）に対する執着を手放すこと**です。時間帯制限を残すということは、「自分たちの組み上げた理論（OFIやδ*）を完全に信用しきれていない自己防衛本能」の現れです。いずれはこの制限を段階的にフェードアウト（設定値の完全緩和化）させ、本質的指標（OFI等）に判断を明け渡す覚悟が必要です。

## §2. 546#(著者) と 547#(Codex) の見落としている「盲点」

Codexによる547#のレビューは、極めて理性的であり特に「これ以上の動的化の前にLive検証が必要」という指摘は完全に同意すべきものです。しかし、546-547の議論の中には**重要な因果関係の見落とし**が存在します。

### 2.1 Codex (547#) の盲点：`preflight_insufficient` と Pipeline は無関係ではない
Codexは「最大blockerは `preflight_insufficient`（在庫や資金の偏り）で31.1%もある。それなのに541-545#はoffset/pricingに寄り過ぎている。参加可能性を先に直すべき」と指摘しました。

一見正論ですが、**なぜ在庫（Inventory）が偏って `preflight_insufficient` が多発するのか**という本質を見落としています。
在庫が限界に達するのは、**「逆選択（Adverse Selection）によって不利な側の注文ばかりを一方的に食わされ、反対側の注文が約定しない（取り残される）」**からです。つまり、PipelineがToxic Flowを正しく弾けず、あるいはスプレッドを正しく広げられなかった**「Pricingの失敗」こそが、`preflight_insufficient`の根本原因**なのです。
したがって、543-545#のPricingの高度化（OFIやδ*による防御）は、実は最大のblockerである在庫偏りを防ぐための直接的な解決策になり得ます。

### 2.2 著者 (546#) の盲点：動的化の「合成の誤謬」による安全倒れ
546#の実装では、以下の制御を導入しました。
- OFIに基づくSpread Boost
- Toxicity Level に基づく Sidecar の Confidence 減衰
- Quadratic Shaping（弱いシグナルの中央をさらに抑制）

これらは個別の理論としては正しいのですが、**全てが「より保守的に働く（掛け算で出力が小さくなる・遠ざかる）」方向のバイアス**を持っています。
個々の防御策が同時に発火した際、「Toxicityが少し高くて、OFIも少し悪くて、Shapingもかかった結果、Sidecarの影響力がゼロに圧縮される一方でスプレッドは極端に広がり、**実質的に市場から締め出される（誰も買ってくれない位置に注文を置く）**」という新たなサイレント・クランプ（見えない飽和）を引き起こす危険性があります。

## §3. 次の一手（Next Steps）への提言

上記の本質論を踏まえ、フェーズ4の中盤以降の進め方を以下に補正します。

1. **547#の提言通り、Same-SHAでのLive検証を最優先とする**
   - 理論をこれ以上積み重ねるのを止め、まずは現状の 540-546# のパッチでfill_testを単一SHA環境で稼働させ、生のテレメトリを収集します。
2. **「時間帯制限」の扱いの変更準備**
   - YAMLにある時間帯キルのフラグをいきなり消す必要はありません（安全網として）。ただし、Live検証において **「時間帯制限でBlockしたとき、OFIやδ*も同じように危険水域を示していたか？」** の相関関係（Overlap）を分析します。OFIが検知できているなら、時間帯制限という補助輪は段階的に外す決定が下せます。
3. **`preflight_insufficient` に対する「Pricing効果」の検証**
   - Live稼働後のデータで、`preflight_insufficient` の発生率が低下するかを観察します。もし低下していれば「我々のPricing高度化は間違っていなかった」という強力な証明になります。
