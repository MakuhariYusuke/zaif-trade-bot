# Gemini 3.1 Pro: 340〜350 および 349# プロンプトの統合レビュー

## 1. エグゼクティブ・サマリー（利益最優先の視点から）

直近のセッション（340#〜350#）におけるバグフィックス群（符号の逆転修正、EWMA導入、alance_forced_switchの撤廃）は、システムを「自爆的なデッドロック」から「評価可能な土俵」へと引き戻した点で**技術的に必須かつ不可欠な応急処置**でした。しかし、これらは全て**防波堤の穴埋め（Safety/Livenessの回復）**に過ぎず、利益を創出する（Profitability）エンジンではありません。

349#の7日間分析で露呈した **uy PnL: -97.3 bps（特に uy_ranging: -102.9 bps）という壊滅的な損失** は、「制御ループのバグ」ではなく「市場理論の欠落」を意味しています。
本レビューでは、349#プロンプトで要求された「正確性・エッジケース・設計判断」に解答しつつ、Codex (350#) の指摘をさらに一段深くえぐり、最高利益化へのパラダイムシフトを提言します。

## 2. 349# 提示課題への回答（EWMA実装の監査）

### Q1. 正確性: _rebuild_ewma_from_history() の再構築ロジックは正しいか？
**Gemini 3.1 Pro 判定: 【致命的な数学的誤り（Look-ahead Bias）】**
コードは sum / len で全履歴の平均をシード（初期値）とし、その上から全履歴を再度 lpha でReplayしています。これは二重カウント（Double Counting）であるだけでなく、**「シード時点（過去）に、未来のデータが入っている」という時系列情報の漏洩（リーク）**を引き起こしています。
*   **利益面での実害**: 再起動時のEWMAが「異常に平均へ引き寄せられた（分散の潰れた）硬直的な値」となり、稼働直後の急変（毒性の強い相場）に対するKill発動が遅れます。
*   **修正必須**: ewma = history[0] として、history[1:] をReplayする標準的な初期化へ書き換えてください（Codex 350# の指摘を全面的に支持します）。

### Q2. エッジケース＆設計判断: P2の 	hreshold * 0.8 は妥当か？
**Gemini 3.1 Pro 判定: 【ロジック破綻リスクあり（Effective Thresholdの無視）】**
現在のTIME LIMIT解除ロジック（sell_dynamic_kill.py）は、ベースの 	hreshold を元に * 0.8 を掛けて安全圏（Reset Target）を作っています。
しかし、同メソッド内で適用されている **「在庫連動緩和（	hreshold_offset_bps）」を完全に無視して計算しています**。
*   **実害**: もし在庫状況によって 	hreshold が一時的に厳格化/緩和されていた場合、固定の * 0.8 という値は「緩和された実際の閾値よりも深い（Kill圏内にある）値」に着地する可能性があり、**「TIME LIMIT解除と同時に即座に再Killされる」デッドロックが復活する危険**を孕んでいます。
*   **修正案**: eset_target = effective_threshold * 0.8 にするか、状態回復をマジックナンバーではなく、時間減衰（Time-weighted decay）に依存させるべきです。

## 3. 市場理論と高収益化への盲点（Blind Spots）

バグが取れた今、私たちが向き合うべき本当の敵（本丸）は **uy_ranging の -102.9 bps** です。売買判定が正常に動いているのにBuyがこれほど負ける理由を、市場の力学的視点で解剖します。

### 盲点 1: 「Ranging」という幻想と遅行するRegime判定
Botが「Ranging（レンジ相場だから両面待ちで稼げる）」と判断している期間中、実際には **「買い手不在のままゆっくりと重力に引かれて下落しているディストリビューション局面」** が発生しています。
Crypto（特にBTC/JPY）におけるレンジ相場は対称ではなく、ファットテール（突発的な下落）を内包しています。現状のBotは「下落トレンド」と判定する**前に**、Bidを置いたまま落下に巻き込まれ（Adverse Selection）、その後 post_fill_30s_pnl がマイナスになって初めて uy_dynamic_kill が発動しています。
*   **結論**: uy_dynamic_kill のような「事後（Post-trade）」のキルスイッチをいくら調整しても、被弾による敗北は止まりません。VPINや直近オーダーブックインバランス（OBI）を用いた**「事前（Ex-ante）のクオート退避・非対称マークアップ」**ロジックを作らない限り、Rangingの皮を被った毒を食い続けます。

### 盲点 2: EWMAの「イベント依存更新」の罠
現在のEWMA（$\alpha = 0.05$）は、約定（Fill）が発生した時にのみ値が更新されます。
*   **実害**: 非常に有毒な相場を検知してKillした場合、新しく約定が起きないためEWMAは**「永遠に悪い値のまま凍結（Stale）」**されます（これがTIME LIMITをハックして無理やり解除しなければならなかった理由です）。
*   **高度なMMの常識**: Kill（または非約定の）期間中は、時間の経過とともに市場環境が「無毒化」している可能性を考慮し、**「イベント（約定）依存」ではなく「時間（秒/分）経過」によってEWMA（またはペナルティスコア）をゼロ（中立）へ自然減衰させるべき**です。そうすれば、不自然な TIME LIMIT * 0.8 ロジック自体が不要になります。

### 盲点 3: Balance Forced の撤廃（348#）の裏側にある「機会損失（Opportunity Cost）」
強制取引を廃止した判断は、Pnlの直接的な悪化を防ぐ見事な止血作業でした。
しかし、Botは依然として「在庫の偏り」を処理しなければなりません。強制取引がないということは、**「在庫が偏ったまま、正常な約定が起きるまで何時間も資金を遊ばせている（Capital Inefficiency）」**ということです。これは見えない損失です。
真の解決策は、Avellaneda-Stoikov（ASモデル）に回帰し、**「在庫が余っている側（売）の提示価格をMidに極限まで寄せ、不足している側（買）を極端に遠ざける（あるいはQuoteしない）非対称なSkewing」**を、今の硬直した maker_price.py にダイナミックに組み込むことです。強制オーダーではなく、受動的オーダーの「位置」で吸い寄せるのです。

## 4. 総括と Next Action

340#〜350#までのアプローチは、火災現場の消火活動としては大成功です。しかし「火が消えた」だけで、まだ「家（利益）」は建っていません。

**短期（P0-P1）のアクションプラン:**
1.  **EWMAロジックの適正化**: _rebuild_ewma_from_history の平均シードの廃止（Double Countingの除去）。
2.  **TIME LIMIT Decay の修正**: 固定の閾値ではなく、在庫連動による effective_threshold ベースで eset_target を算出するよう修正。

**中期（高収益化への転換点）:**
*   DynamicKillManager（事後防衛）への過剰な工数投資を止めます。次は**「Ranging時のBuy Adverse Selectionを約定前に回避する指標（OBI等の追加）」**と**「強制約定に依存しないダイナミック・プライシング（Inventory Skewingの拡充）」**の2点に主戦場を移してください。
