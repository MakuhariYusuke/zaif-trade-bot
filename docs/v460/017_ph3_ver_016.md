## §2 016# が見逃した指摘漏れ

### F9 [CRITICAL] `FeatureSchema` が `@dataclass` 欠落でインスタンス化不能

`ztb/training/core/feature_schema_manager.py` L39-54:

```python
class FeatureSchema:                                     # ← @dataclass がない
    """特徴量スキーマのデータクラス"""
    features: List[str]                                   # ← クラス変数アノテーション（属性として機能しない）
    config: Dict[str, Any]
    scaler_data: Optional[Dict[str, NDArray[...]]] = None

    def __post_init__(self) -> None:                      # ← dataclass 専用メソッド、呼ばれない
        if not self.features:
            raise ValueError("features cannot be empty")

    @classmethod
    def from_dict(cls, data: Dict[str, Any]) -> "FeatureSchema":
        return cls(**data)                                # ← __init__ 未定義のため TypeError
```

**影響**:
- `FeatureSchema(features=[...], config={...})` → `TypeError: FeatureSchema() takes no arguments`
- `from_dict()` も同様に失敗
- `__post_init__` は呼ばれずバリデーションが死んでいる
- 直下の `FeatureSchemaMetadata` は正しく `@dataclass` が付与されており、パターン不整合

**016# との関係**: F4 が「FeatureSchemaManager 拡張を第一案に」と推奨しているが、拡張先の中核データ構造がインスタンス化不能。

**現在の影響範囲**: `FeatureSchema` は外部から使用されていない（`FeatureSchemaMetadata` のみ使用）ため、現状は潜在バグ。しかし 016# P1 の拡張計画の前に修正必須。

### F10 [HIGH] 015# の SB3 ReplayBuffer 注入コードの API 不適合

015# §7.5 の提案コード:
```python
model.replay_buffer.add(
    obs=exp.observation,       # ← keyword arg
    next_obs=exp.next_observation,
    action=exp.action,
    reward=np.array([exp.reward]),
    done=np.array([exp.done]),
    infos=[{}],
)
```

既存の動作例（`experiments/sac_v446_learning_params_optimization.py` L349）:
```python
model.replay_buffer.add(obs, next_obs, action, reward, terminated or truncated, [info])
# ↑ positional args, reward は scalar, done は bool
```

**不適合箇所**:
1. SB3 の `ReplayBuffer.add()` は **positional args** を使用（keyword arg は互換性依存）
2. `reward` は `np.array([exp.reward])` ではなく scalar `float(reward)` が適切
3. `done` も `np.array([exp.done])` ではなく `bool` が適切
4. 内部バッファは `(buffer_size, n_envs, *obs_shape)` で初期化されるため、n_envs=1 の場合 `obs` は `(1, obs_dim)` にreshape が必要な場合がある

015# の設計提案をそのまま実装すると、サイレントな shape mismatch または TypeError が発生する可能性が高い。

### F11 [HIGH] HeavyTradingEnv ↔ FastIntradayEnvV456 のインタフェース差異が未網羅

016# F2 は「HeavyTradingEnv 前提」を指摘したが、移行のための差異分析が欠落:

| 観点 | HeavyTradingEnv | FastIntradayEnvV456 |
|------|-----------------|---------------------|
| **行動空間** | `Box([-1],[1])` 1D | `Box([-1,0],[1,1])` **2D** (default) |
| **観測次元** | 可変 (`len(feature_columns)`) | **固定 88D** (30/27/6/6/13/6) |
| **正規化** | config 依存 | `GroupedFeatureScaler` (online, clip=3.0) |
| **コンストラクタ** | `(df, config, optimizer_tracker)` | `(df, base_cols, mtf_cols, regime_cols, ...)` 10+ 引数 |
| **報酬関数** | 環境内蔵 (多種) | `compute_hft_reward()` 外部関数 |
| **次元検証** | なし | `raise ValueError` (ハードコード) |

「別チケット化」の推奨は妥当だが、チケットの工数見積もりにはこの差異表が不可欠。

### F12 [HIGH] 行動空間 1D/2D 設計矛盾の未指摘

015# §6.4 で「ph3 では 1D 連続を推奨」と記載:
> maker-only で TTL は maker 側ロジックで管理するため、RL が決めるべきは「どの程度のポジションを取るか」のみ。

FastIntradayEnvV456 のデフォルト行動空間（L106-110, L147）:
```
Action Space Type: "2d_position_ttl" (default)
  Box([-1, 0], [1, 1])
    - target_position: [-1, 1]
    - ttl_fraction: [0, 1]
```

1D への切替は `action_space_type="1d_position"` で可能だが、015/016 のどちらも以下を考慮していない:
- 2D → 1D 切替時の既存モデル互換性（全既存モデルが使用不能になる）
- TTL を RL から外すことの妥当性（TTL 管理は maker 戦略の重要パラメータ）
- HeavyTradingEnv の 1D と FastIntradayEnvV456 の 1D はインタフェースが異なる

### F13 [MEDIUM] 報酬関数が maker-only 執行特性を未反映

`compute_hft_reward()` (`ztb/trading/rewards/fast_intraday.py`) の構造:
```
r_t = pnl - fee_paid - slippage_paid - (fee_paid + slippage_paid) * fee_penalty_weight
```

v460 maker 0% 環境での問題:
1. **`fee_paid` が常に 0** → `fee_penalty_weight` のロジックが全て無効化
2. **即時約定を仮定** → maker 注文のキュー待ち/fill uncertainty を反映しない
3. **adverse selection 概念なし** → 000# G1.1-exec で測定する AS ratio が報酬に組み込まれていない
4. **fill rate の確率的要素なし** → `step()` で常に約定する前提

015# §8.1 質問 3 で「報酬の遅延評価」を提起しているが、**報酬関数の構造自体の不適合**は議論されていない。016# も完全に見落としている。

### F14 [MEDIUM] G2-train 測定方法の転記欠落

015# §8.3 は Gate 閾値を正確に転記しているが、000# §3.4 の測定方法:
```
| 条件 | 測定方法 |
| gross > 0 の seed 比率 | 4 seed × 50K steps |
```
この「4 seed × 50K steps」が 015# に記載されていない。ph3 の実行計画で seed 数/ステップ数が不明確になるリスクがある。016# F8 は節番号の誤りのみ指摘し、内容の欠落には言及していない。

## §6 結論

016# の問題発見力は高く、F1-F8 の全指摘が実コードで裏付けられた。

一方、以下の構造的盲点が存在した:

1. **「解決策の実行可能性」の未検証** — F4 で FeatureSchemaManager を推奨するも、推論側 (`action_prediction.py`) が schema を使わない事実と、`FeatureSchema` 自体のバグを見逃した

3. **設計提案の API 適合性** — 015# §7.5 の SB3 API 使用法の誤りを検証していない (F10)

**ph3 着手前の最重要アクション**: P0 の 3 タスク（ActionPrediction 修正、FeatureSchema 修正、sac_train 枠追加）を ph2 と並行で実施すべき。
