## 1. 590# / 591# における致命的なデータ誤読と論理的破綻

### 1.1 [破綻] 591# §1.2「ev_offsetがテール損失の根本原因である」という錯誤
- **591# の主張**: *「tail 36件、AS率100%、decision_path=ev_offset 100%。したがって ev_offset 経路の参加条件を削る方が期待値改善につながる」*
- **検証結果 (ログ直叩き)**:
  `fill_records_*.jsonl` から `fill_price` が存在する（約定した）レコードの `decision_path` を抽出した結果、**全体の 99.6% (2408/2417) が `ev_offset` でした。**
  つまり、約定した注文はほぼ全て `ev_offset` パスを通っており、テール損失の100%が `ev_offset` になるのは**単なるベースレート（母集団の偏り）であり、因果関係ではありません。**
- **金融工学的見地**:
  真の問題はパスの名前ではなく、`skip_gate_ev_weighted.py` のロジックにあります。EVスコアが悪い（=逆選択リスクが高い）場合、モデルは本来「スキップ」を推奨していますが、現在の仕様はそれを「オフセット乗数（スプレッド拡大）」に変換して無理にクオートを継続しています。強い毒性フローに対してスプレッドを数bps広げても、アービトラージャーには軽々と食い破られます（Adverse Selection）。

### 1.2 [破綻] 590# P1「macro_strong_down の防御強化」は幽霊との戦い
- **590# の主張**: *「macro_strong_down で -1.79 mean。特に 548dda24 で -77.6 集中しているため、この防御策が P1 (HIGH)」*
- **検証結果**:
  JSONLをSHA単位で再集計したところ、`macro_strong_down` による損失の100%は数日前の古いSHA（`548dda24`, `5a546923`）で発生しています。**極めて重要な事実として、現在の最新SHA (`c164d21d`) では `macro_strong_down` での約定（およびサイクル実行）は「0件」です。**
  既に過去の改修で排除・回避されているか、発生していない事象に対して P1 の工数を割くのは完全な無駄（オーバーエンジニアリング）です。

### 1.3 [幻覚] 591# §1.5 CV Lead-Lag の数値捏造
- **591# の主張**: *「buy では 236/447 fills と多く... sell では 19/352 fills と少なく」*
- **検証結果**:
  `analyze_fill_logs.py` の実出力は **「buy: 155 fills, sell: 101 fills」** です。Codex 591# は全く存在しない数値を幻覚（Hallucination）として出力し、それを基に buy/sell の非対称性を論じています。このセクションのアドバイスは破棄すべきです。

## 2. 実データに基づく真の残課題 (Current SHA: `c164d21d`)

Codex 591# が指摘した通り、最新の `c164d21d` では **Sell は +1.79 bps に黒字化** しており、全体を壊す必要はありません。一方で、以下の課題が残っています。

**CV Lead-Lag 指標の「Widen（拡大）」による被弾**:
- `c164d21d` の Buy 側における CV 適用時は **-3.21 bps** という壊滅的な結果です。
- ログの内訳を見ると、`widen=5, cap_hit=6` となっており、システムは**意図通りにLead-Lag（先行市場の急落）を検知し、スプレッドを広げて防御しようとしています。**
- しかし結果は大幅なマイナスです。これは「他市場の急変を検知した際、クオートを遠ざける（Widen）だけでは被弾を免れない（テイカーの勢いの方が深い）」ことを実証しています。

## 3. 金融工学的「儲かる」Alpha 提案とその実装・実現性 (深堀り)

前章の事実検証を踏まえ、現状のアーキテクチャに適合しつつ、短期高収益に直結するアイディアを提案します。今回は「本当に実装できるのか？」「現実的か？」という視点から、具体的なコードイメージと実現性を深掘りします。

### 提案A: Toxic検知時の "Widen to Skip" 変換 (即効性: 最高 / 工数: 最小)
- **概念**: EVスコア（予測PnL）が著しく悪い場合、現在のシステムは「スプレッドを広げて待ち構える（Widen）」挙動（`ev_offset` パス）をとります。しかしHFTアービトラージャーに対して数bps広げても壁ごと食い破られます。「毒性が強いなら広げるのではなく逃げる（Skip）」というルールへ回帰させます。
- **実装イメージ**:
  `scripts/v460/lib/skip_gate_ev_weighted.py` におけるEVスコアの処理を修正します。現状は `compute_ev_offset_multiplier` に渡して乗数を決定していますが、ここにハードスキップ閾値を設けます。
  ```python
  # YAML設定値: skip_gate_ev_toxic_skip_threshold: -5.0 など
  if ev_score < config.skip_gate_ev_toxic_skip_threshold:
      # offset で広げるのをやめて、完全にサイクルを放棄する
      return SkipDecision(
          should_skip=True,
          predicted_pnl_bps=ev_score,
          reason="ev_toxic_skip",  # 新規パス
          model_used="ev_weighted"
      )
  ```
- **実現性と評価**: **極めて現実的かつ即効性があります。** 実装は数行のIF文の追加とYAMLのキー追加のみで完結し、既存の乗法/加法パイプラインに一切の悪影響を与えません。アービトラージによる10bps級のテール損失を根本から遮断でき、現在の「広げたところで狩られる問題」を即座に解決できます。

### 提案B: 連続的 OBI(OFI) に順張りする非対称 Inventory Skew (即効性: 中 / 工数: 中)
- **概念**: 在庫が偏った際、現在のシステムは「逆サイドのクオートを厚くする（在庫吐き出し）」という Inventory Skew をかけます。現在、トレンド検知時（`inv_skew_regime_gate_enabled = True`）にはこれを完全にOFFにしていますが、これは「ゼロかヒャクか」のバイナリ制御です。OFI（オーダーフロー）の強さに応じて、Inventory Skew を**連続的（S字カーブ等）に割引（Discount）**することで、トレンド中の機会損失と在庫リスクのバランスを取ります。
- **実装イメージ**:
  `scripts/v460/lib/maker_price.py` の `_apply_inventory_skew` メソッドを改修します。
  ```python
  # 現状の tanh 平滑化係数
  _raw_factor = _imb * _sign * cfg.inventory_skewing_max_factor
  
  # OFI (短期モメンタム) が自分の在庫と同方向なら、吐き出しを我慢する (0.0 ~ 1.0)
  # adverse_ofi がプラス(不利方向) = 自分が吐き出したい方向へのモメンタム
  momentum_discount = max(0.0, 1.0 - (self._last_ofi_lite * _sign * cfg.inv_skew_momentum_sensitivity))
  
  # スキュー係数をモメンタムで割引く
  _factor = math.tanh(_raw_factor) * momentum_discount
  ```
- **実現性と評価**: **現実的であり、金融工学的にも正統なマーケットメイク制御（Inventory-Momentum Interaction）です。** ただし、調整ミスにより「在庫を永遠に抱え込んで Preflight Insufficient（残高不足）で停止する」リスク（ダンプリスク）が伴います。提案Aの「Skip機能」と併用するか、絶対的な時間切れ決済（Time-in-Force）での在庫放出を担保する安全網の確認が前提となります。

### [追加] 提案C: CV Lead-Lag の完全非対称化「Maker Post-Only Retreat」
- **概念**: `cross_venue_lead_lag` 機能は現在、指定閾値(6.0bps等)以上で `veto` (ハードスキップ) を発動します。しかしログの通り、閾値未満の「Widen（拡大）」では -3.21 bps の損失を出しています。
  Zaifのような低流動性取引所では、外部取引所（Binance等）をシグナルにしたアプローチは有効ですが、**ZaifのAPIレイテンシ限界**を考慮するとキャンセル注文が間に合わず被弾します。したがって、CV Lead-Lag を「Widenさせる機能」ではなく、「危ない側のクオートを即座に取り下げる（片側クオートへの移行）」専用のトリガーとして再定義します。
- **方向修正の提案**: Widen機能（オフセット乗数の引き上げ）を廃止し、CVで `adverse_side` を検知した瞬間に、その Side の注文を一時的に `sell_dynamic_kill` のように完全に無効化（Drop）し、favorable 側のみの Maker とする。
