## 技術詳細分析

### 問題の系統

```
既存スクリプト (5000-step版)
  ├─ 訓練: 成功 ✓ (5000ステップ実行)
  ├─ 結果: 4,948 エピソード生成
  └─ 品質: Critical Issue 検出 ❌
  
改善スクリプト (30,000-step版)
  ├─ 設定: drawdown 0.1→0.3, initial_balance 124→50000
  ├─ 期待: パラメータ改善で Issue 解決
  └─ 結果: ステップ 1 で即座に失敗 ❌
```

### 隠れていた環境問題

```
FastIntradayEnvV456.step() のロジック:

1. action 実行 (ランダムなので-100% 空売りの可能性)
2. reward 計算: fee/slippage で -0.25 程度のマイナス報酬
3. balance 更新: balance -= reward × scaling
4. drawdown チェック: if balance < initial_balance * (1 - 0.1)
5. done 判定: true → エピソード終了

問題: reward が balance に直接反映され、
      初期数ステップでドローダウンリミットを超過
```

### なぜ 5000-step は「成功」したのか

**仮説**:
- SAC の initial learning_starts = 10,000 により、
  最初の 10,000 ステップはバッファ収集のみで実際の学習なし
- つまり、短いエピソード群が快速に生成され、
  バッファが満杯になる前に十分なデータを収集
- その後、学習開始時には既に多様なデータが蓄積
- ただし、その学習データが「100% HOLD」という
  最悪の収束に至った

**現実**: 
- 5000-step の訓練は「成功」ではなく「走破」に過ぎない
- 結果として生成されたモデルは実用的でない状態
