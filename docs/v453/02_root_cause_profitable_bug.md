# v453 "Profitable Bug" Root Cause Analysis

## 1. 調査目的
なぜ「バグあり（レジームが正しく渡されない）」バージョンが、修正版よりも高いパフォーマンス（Total Return 12.43% vs 6.05%）を記録したのか、そのメカニズムを解明する。

## 2. 調査結果

### 2.1 ThresholdManager の挙動検証
`analysis/debug_threshold_logic.py` による検証結果：

| Regime Input | Threshold (Base=0.01) | Multiplier | 備考 |
| :--- | :--- | :--- | :--- |
| **None** (Buggy) | **0.0101** | **~1.0x** | バグあり版の挙動。ほぼ素通し。 |
| **"Unknown"** | **0.0101** | **~1.0x** | 明示的に不明な場合も同様。 |
| **"CONSOLIDATION"** | **0.0101** | **1.0x** | **現在の修正版 (Final Solution)**。 |
| **"CONSOLIDATION"** | *0.1010* (推定) | *10.0x* | **修正直後 (Performance Drop)**。 |
| **"STRONG_BULL"** | 0.0050 | 0.5x | トレンド時は閾値を下げてエントリーしやすくする。 |

### 2.2 メカニズムの解明

1.  **バグあり版 (Baseline)**:
    - `HeavyTradingEnv.step` が `ThresholdManager` に `regime=None` (または "Unknown") を渡していた。
    - `ThresholdManager` は `if regime:` ブロックをスキップし、**Multiplier 1.0** を適用した。
    - 結果：`CONSOLIDATION` や `RANGING` 相場でも、閾値が低いまま（0.01）維持された。
    - モデル（SAC）はレンジ相場でも微小な利益を出せるシグナル（例: 0.02〜0.05）を出力しており、これが閾値を通過して約定し、利益 (+6,000円) を積み上げた。

2.  **修正直後 (Performance Drop)**:
    - `HeavyTradingEnv` を修正し、正しいレジーム ("CONSOLIDATION") を渡すようにした。
    - `ThresholdManager` は仕様通り `adjusted_threshold *= 10.0` を適用し、閾値が **0.10** に跳ね上がった。
    - 結果：モデルが出力していた微小な利益シグナル（0.02〜0.05）が全てブロックされ、レンジ相場での利益が消滅した。

3.  **最終解決版 (Final Solution)**:
    - `ThresholdManager` の設定を変更し、`CONSOLIDATION` 時の倍率を **1.0** に戻した。
    - これにより、正しいレジームを受け取りつつも、バグあり版と同じ「低閾値」で動作するようになり、利益機会を回復した（ただし完全には戻らず、+1,383円止まり）。

### 2.3 なぜ完全回復しなかったのか？
- バグあり版では `regime=None` だったため、`ThresholdManager` 内の他の微細なロジック（例えば `adaptive_mode` の分岐など）が、`regime="CONSOLIDATION"` (倍率1.0) の場合と微妙に異なる挙動をした可能性がある。
- または、`HeavyTradingEnv` 側でレジームが "Unknown" であることが、他のコンポーネント（RewardCalculatorなど）にも影響を与え、それがプラスに働いていた可能性も否定できない。

## 3. 結論
「バグで勝てた」理由は、**「レンジ相場での過剰な取引抑制（閾値10倍）が、バグ（レジーム不明）によって無効化されていたから」** である。
現在のモデルはレンジ相場でも利益を出せる能力を持っているため、この抑制機能は不要（むしろ有害）であった。

## 4. 教訓
- **過剰なヒューリスティックの弊害**: 過去のモデル（v451）で必要だった「レンジでの取引抑制」が、進化したモデル（v453）では足かせとなっていた。
- **バグの効用**: バグが偶然にも「古い制約」を解除する役割を果たし、モデルの真の実力を引き出していた。
- **正しい修正**: バグを直すだけでなく、制約（設定）も見直すことで、健全なコードと高いパフォーマンスを両立させる必要がある。
